\section{Introduction}~\label{sec:introduction}
The streams we consider both insert and delete keys, which amount to
incrementing and decrementing the key's count, respectively. While some
applications such as tracking click-through rates in webpages only require
insertions, deletions are needed for other applications such as maintaining
count estimates for SQL tables for use in a query optimizer. 

We define the following two goals: \textbf{(G1)~Space-Efficient Counters}, and
\textbf{(G2)~Scaling Error with Stream Length}.

\textbf{Applications.} 
Due to its simplicity and high accuracy under skewed workloads, CMS is used in
many applications, including $k$-mer counting in
bioinformatics~\cite{CMSkmer,SetMinSketch}, network
monitoring~\cite{SketchBasedChangeDetection,WhatsNew,TrafficManagementSurvey},
and hardware security systems~\cite{CoMeT}. Yet, its biased estimates make it
less useful for applications such as join size estimation. As shown in
\Cref{sec:cs}, the Count Sketch is the tool of choice for these settings.

Since CS provides unbiased estimates, it is used in applications where
estimates are combined or multiplied to derive more complex statistics. In
particular, unbiased estimation is crucial for query
optimization~\cite{Compass,QueryOptimizationSketches,ConvolutionSketch} and
covariance estimation~\cite{ASCS}, as count estimates are multiplied in these
contexts, amplifying any bias. Other applications benefiting from CS include
feature selection~\cite{MISSION} and similarity
search~\cite{CSSetSimSearch,DensifyingLSHSketches,LasVegasSimSearch,DistanceSensitiveBloomFilters}.
CS also provides \emph{Universality}~\cite{UniversalSketching}: the ability to
estimate many statistics based on the key frequencies. This makes it a general
measurement tool for networks since it allows administrators to collect
diagnostics of any kind without needing to explicitly define the required
statistics (such as the mean, variance, and moments) beforehand~\cite{UnivMon}.

As MG accurately tracks the frequencies of hot keys, many other sketch designs
use it as a sub-component to reap its benefits. Moreover, because it also
stores the keys themselves, unlike CMS and CS, it is used to report the hottest
keys, trending keys, and much
more~\cite{BatchUpdateMisraGries,AugmentedSketch,BitMatcher,BubbleSketch,HeavyGuardian,HeavyKeeper,JigsawSketch,MVSketch,SketchVisor,WavingSketch,MicroscopeSketch,PSketch,TightSketch}.

\section{Background}~\label{sec:background}
A stream is a sequence of key-value pairs~$\left\langle (x_1,\Delta_1),
(x_2,\Delta_2), \dots \right\rangle$, where~$x_i$ is the $i$-th key that
appears in the stream and~$\Delta_i = \pm1$ represents whether its count was
incremented due to an insertion ($\Delta_i=1$) or decremented due to a deletion
($\Delta_i=-1$). This is known as the \emph{General Turnstile Model} of data
streams~\cite{StreamModels}. We denote key~$x$'s count by~$f(x)$, and represent
the current total count of the keys in the stream with~$N=\sum_x f(x)=\sum_i
\Delta_i$. \Cref{tab:term_and_symbol_definitions} lists the terms and symbols
used throughout the paper.

\textbf{Exhaustive Approach.}
The simplest approach to tracking frequencies is to store each key and its
count in a hash table. Although this approach is fully accurate, it entails a
high memory overhead for three reasons: (i)~It stores all keys in the stream.
Variable-length keys worsen this overhead since they require an indirection
layer (e.g., pointers). (ii)~It stores one counter for each unique key.
(iii)~The hash table may occasionally be as much as half empty to support
collision resolution and expansions. These different overheads multiply with
the number of streams the application monitors. Problems~(i) and (ii) imply a
memory footprint that is linear in the number of unique keys in the stream,
which can be of the same magnitude as the total key count~$N$.

%(3)~Since the counters are fixed-length, each of them must be long enough to accommodate the maximum count, even if most keys have a very low count.

Frequency estimation sketches address these problems by trading accuracy for
space. That is, for any key~$x$, a sketch returns an estimate~$\hat{f}(x)$ of
$x$'s count~$f(x)$. We focus on Count-Min Sketch~\cite{CountMin} for now, as it
is the simplest and most widely used
sketch~\cite{ADSMassiveDatasetBook,SketchesTrafficManagementSurvey}. Later, we
describe Count Sketch~\cite{CountSketch} (\Cref{sec:cs}) and
Misra-Gries~\cite{MisraGries} (\Cref{sec:mg}) and apply our techniques to them.

\textbf{Count-Min Sketch (CMS).}
The core design element of CMS is a counter array consisting of~$w$ counters,
each initialized to zero. We insert a key~$x$ into this array by hashing it to
one counter and incrementing it. We delete~$x$ by decrementing its
corresponding counter. The counter that key~$x$ hashes to provides an estimate
of~$x$'s count. Due to hash collisions, multiple keys can map to the same
counter. Because of this, we may overestimate the count of a key~$x$. This
error is at most~$\frac{N}{w}$ in expectation since a key participates in a
hash collision with a probability of~$\frac{1}{w}$ and the total count of keys
different from~$x$ is at most~$N$. Increasing the array's size makes collisions
less likely, thereby decreasing the error and improving \emph{Accuracy}. Even
so, the error may deviate from its expectation. The probability that errors do
not exceed the expectation ``too much'' is known as the sketch's
\emph{Confidence}. A straight-forward application of Markov's inequality shows
that the error does not exceed~$\frac{eN}{w}$ with a confidence of at
least~$1-1/e$, i.e., $\Pr\left( |\hat{f}(x)-f(x)| \leq \frac{eN}{w} \right)
\geq 1-1/e$ for any key~$x$. Here, we use Euler's constant~$e$ due to
convention. Any other constant would also work and would replace~$e$ in both
the accuracy bound and the confidence. This implies that the smaller the
constant becomes, i.e., the more accurate we expect the sketch to be, the lower
confidence drops.

Yet, with a single array, confidence is low ($\approx 63\%$). The reason is
that all keys sharing the same counter as a frequent key will suffer from
inflated estimates. Moreover, since there are many keys with low or moderate
counts, there is a non-negligible chance that enough of them map to the same
counter and inflate estimates beyond the error bound. CMS addresses these
issues by allocating~$d$ independent counter arrays, each with a dedicated hash
function~$h_i$. CMS inserts or deletes a key by applying the operation to each
array, and it answers a query by querying all arrays and taking the minimum of
the estimates.\footnote{CMS uses pairwise-independent hash functions to bound
the probability of collisions and overestimation~\cite{CountMin}.}
\Cref{fig:cms_overview} shows an example of insertions and queries applied to
three counter arrays. Returning the minimum for queries boosts confidence
exponentially, since it only carries severe errors when all estimates err
significantly. CMS ensures an error of at most~$\frac{eN}{w}$ with a confidence
of~$1-e^{-d}$, i.e., $\Pr\left( |\hat{f}(x)-f(x)| \leq \frac{eN}{w} \right)
\geq 1-e^{-d}$ for any key~$x$.

Since CMS uses a constant number of tightly packed counters and does not store
the stream's keys, it significantly improves the memory footprint compared to
the exhaustive approach of tracking each key's exact count. Nevertheless, CMS
still suffers from several memory inefficiencies, as we show in the following
section.

\section{Problem Analysis}\label{sec:problem_analysis}
CMS often uses far more memory than necessary by using (P1)~fixed-length
counters and (P2)~fixed-size arrays.

\hypertarget{problem:fixed_length_counters}{\textbf{(P1)~Fixed-Length Counters.}}
CMS uses fixed-length counters. To prevent overflows, each counter must be long
enough to fit the maximum counter value, which may be of the same magnitude as
the total key count~$N$. Since workloads are often skewed, most counters are
typically small and many of their bits are unused.

Ideally, each counter should be just long enough to fit its value. This would
save space, or, conversely, enable having more counters under the same memory
budget to improve accuracy. One approach is to compress the counters using
algorithms such as compressive sensing~\cite{TreeSensing,BitSense} or
hypergraph peeling~\cite{CodingSketch}. Yet, these methods introduce heavy
decompression overheads to queries.

Another approach is to implement variable-length counters by using short
counters upfront and allowing overflows to spill into ``shared'' counters. For
example, \cite{SALSA} merges an overflowing counter with an adjacent counter to
create a longer counter that aggregates their value. Other
variants~\cite{BitSense,PyramidSketch,StingySketch,AdaptiveCounterSplicing,CounterTree,TreeSensing}
allocate a small number of counter fragments, each acting as the higher-order
bits of multiple short counters. Counter sharing negatively impacts accuracy,
as it blows up the estimates of keys mapping to a small counter that is merged
with a large counter. Accuracy further deteriorates when keys are deleted, as
counter sharing ambiguates how counters should be ``separated'' as they
decrease. Moreover, counter sharing couples the counter values, complicating
the integration of other orthogonal techniques like Bayesian inference for
improving accuracy~\cite{BayesianSketches,BFES} and convolution for join size
estimation~\cite{ConvolutionSketch}. 

\hypertarget{problem:fixed_size_sketch}{\textbf{(P2)~Fixed-Size Sketch.}}
Many applications monitor continually changing streams. In such scenarios, the
total key count~$N$ can grow over time and is therefore unknown upfront. Since
the error of a fixed-size CMS (and other sketches) scales linearly with~$N$,
practitioners are faced with the challenge of controlling the sketch's error by
tuning the number of counters in each array without knowing the ultimate value
of~$N$. The crux of the problem is that if there are too few counters in each
array, the estimates will have significant errors. If there are too many
counters, memory is wasted. Moreover, $N$ may fluctuate over time due to the
stream having both insertions and deletions. The ideal sketch must scale its
memory footprint with~$N$ to bound the error without wasting space, thereby
guaranteeing sub-linear errors.

%Counting attribute values in SQL tables for OLTP or HTAP workloads and periodically collecting network activity reports for administration are examples of such applications. 

\textbf{Summary.}
Although much research has gone into
resolving~\hyperlink{problem:fixed_length_counters}{(P1)} with space-efficient
counters, existing sketches either (i)~suffer from the accuracy issues of
counter sharing, (ii)~are slow, or (iii)~have accuracy drops when deleting
keys. Moreover, no work to date has attempted to
address~\hyperlink{problem:fixed_size_sketch}{(P2)}. Is it possible to design a
sketch that resolves~\hyperlink{problem:fixed_length_counters}{(P1)} and
\hyperlink{problem:fixed_size_sketch}{(P2)} while maintaining high performance
and accurate support of deletions?

\section{\sketch}\label{sec:sketchbook} 
We present \sketch, a framework for generalizing a frequency estimation sketch
to adapt its memory footprint to the workload's skew and the stream's length.
\Cref{sec:accommodating_skew} shows how to adapt to skew by compactly encoding
each counter as a short integer and extending it as it overflows, addressing
problem~\hyperlink{problem:fixed_length_counters}{(P1)}.
\Cref{sec:accommodating_unknown_stream_lengths} shows how to control both
accuracy and space for streams of unknown length by expanding and contracting
the sketch, resolving problem~\hyperlink{problem:fixed_size_sketch}{(P2)}. Our
techniques ensure a reduction in memory footprint while maintaining high
performance and supporting deletions. We first describe \sketch\ as applied to
the Count-Min Sketch~(CMS), denoted as \sketchcms. We apply it to other
sketches in Sections~\ref{sec:cs}~and \ref{sec:mg}.

\subsection{Accommodating Skew}\label{sec:accommodating_skew}
Under skewed workloads, few counter values are large, and most are small. In
contrast, under more uniform workloads, most counter values are similar. To
handle all workloads in the least space possible, \sketchcms generalizes CMS to
support variable-length counters. It starts by storing the counters in
fixed-size integers called \emph{Stubs}. It chooses the shortest length
possible for the stubs based on the workload's skew so that they fit the values
of most counters. It elongates a counter whose value overflows its stub with a
dedicated variable-length \emph{Extension}. While the extensions require
slightly more space due to the need for delimiters, the space saved by encoding
most counters in short stubs far outweighs this overhead. \sketchcms quickly
locates the extension of an overflowing counter using a bit manipulation
workflow that leverages rank and select operations.

\textbf{Chunking.}
To speed up manipulating counters, \sketchcms partitions each counter array
into contiguous \emph{Chunks}, each occupying a 512-bit cache line. A chunk
stores the stubs of its counters while tracking the counters that overflow
their stubs using an \emph{Overflows Bitmap} with one bit per counter. A chunk
also stores the extensions of the overflowing counters contiguously in the
remaining space towards its end, called its \emph{Extension Pool}. Counter~0
and Counter~1 in \Cref{fig:counter_chunk} are examples of a non-overflowing and
overflowing counter within a chunk, respectively.

\textbf{Parameters.}
\sketchcms has two tunable parameters: the length, in bits, of each stub~$s$
and the number of counters per chunk~$c$. With more skewed workloads, having a
shorter stub length~$s$ and more counters per chunk~$c$ reduces space
consumption. The reason is that skew shrinks most counter values, enabling the
use of shorter stubs for storing them. Skew also reduces the average length of
the extensions, leaving more space in a chunk to store more counters.

We discuss how to adapt the tuning of these parameters to the workload as the
stream evolves in \Cref{sec:accommodating_unknown_stream_lengths}. We illustrate the
impact of this procedure on the memory footprint in \Cref{sec:evaluation}.

In particular, when the workload is fully uniform and all counter values are
expected to be similar, we adaptively tune the length of the stubs so that all
counters fit in them. This allows us to remove the overflows bitmap from all
chunks and pack them with stubs, yielding a configuration that corresponds to a
standard CMS.

\textbf{Extensions.}
We form extensions from 2{\nobreakdash-}bit \emph{Fragments} to encode the
higher-order bits of overflowing counters succinctly and to extend them at the
finest possible granularity. We use the fragment~$11$ as a delimiter at the end
of each extension. We use the other three combinations of bits to encode each
extension's value in base 3. Specifically, we represent the
base{\nobreakdash-}3 digits~$(0)_3$, $(1)_3$, and $(2)_3$ as the
fragments~\textit{00}, \textit{10}, and \textit{01}, respectively. We store
fragments in increasing order of their digits' significance from left to right.
Formally, we encode a value~$v$ in an extension by representing each of
its~$\left\lfloor \log_3 v \right\rfloor + \nolinebreak 1$ digits in a
fragment, with the~$j${\nobreakdash-}th digit being~$v_j=\left\lfloor v/3^j
\right\rfloor \mod 3$. We decode~$v$ back into decimal by computing the
sum~$3^0 \cdot v_0 + 3^1 \cdot v_1 + \dots$.

For example, the value~5, which is the value of the higher-order bits of
Counter~1 in \Cref{fig:counter_chunk}, has two digits in base 3. It is
therefore encoded as the extension~$\langle (2)_3, (1)_3, \text{delimiter}
\rangle=\langle \text{\textit{01}}, \text{\textit{10}}, 11 \rangle$. Decoding
this extension yields~$3^0 \cdot 2 + 3^1 \cdot 1 = 5$, as expected.

Forming a chunk's extensions from 2-bit fragments allows them to fit in 1-2
machine words in most cases. We prove in \Cref{sec:theoretical_analysis} that
using these extensions in conjunction with short stubs enables a chunk to
encode each counter's value in space close to the length of its binary
encoding.

\textbf{Locating an Extension.}
To decode an overflowing counter, \sketchcms must locate its extension. To this
end, it keeps the extensions in the same order as that of the counters. It
locates the~$i${\nobreakdash-}th counter's extension by counting the number of
preceding bits set to~1s in the overflows bitmap. This is equivalent to the
number of overflowing counters preceding the~$i${\nobreakdash-}th counter,
denoted by~$m$. Skipping over the first~$m$ extensions in the extension pool
leads to the position of the target extension.

\Cref{fig:extension_location_example} illustrates the process of identifying
the 3rd counter's extension in a chunk. Here, since the 3rd bit in the
overflows bitmap is~1, the 3rd counter has an extension. As there is one bit
set to~1 preceding the 3rd bit in the overflows bitmap, we skip one extension
to locate the 3rd counter's extension, shown in gray.

\textbf{Fast Access Using Rank and Select.}
\sketchcms quickly locates the extension of an overflowing counter using rank
and select
operations~\cite{Poppy,FlorianRankandSelect,CompactPATTrees,RankandSelectDict,GQF}.
Given a bitmap~$B$, the $\texttt{rank}(i,B)$ operation counts the number of~1s
strictly before the $i$-th bit, and the $\text{select}(i,B)$ operation returns
the position of the~$i${\nobreakdash-}th 1. Later in this section, we show how
to use specialized CPU instructions to implement these operations efficiently. 

The first step is to determine~$m$, the number of overflowing counters to the
left of the~$i${\nobreakdash-}th counter. As this is the number of 1s before
the $i${\nobreakdash-}th bit in the overflows bitmap, \sketchcms applies the
rank operation to evaluate~$m=\texttt{rank}(i,$~overflows$)$.

The second step is to identify the target extension's delimiter by skipping
over the~$m$ delimiters preceding it. We do this using several bit manipulation
techniques. First, we convert the extension pool into a so-called
\emph{Delimiters Bitmap}. This bitmap contains one bit set to~1 at the position
of every delimiter and~0s everywhere else, as illustrated at the bottom right
of \Cref{fig:extension_location_example}. To derive this bitmap, we take the
bitwise-and of the extension pool with a version of itself shifted to the right
by one bit. The result is a bitmap with a~1 at the end of any two
consecutive~1s in the original extension pool, as illustrated in
\Cref{fig:extension_location_example}. This means that every bit in this bitmap
corresponding to the second bit of a fragment is set to 1 if the fragment is a
delimiter and is set to 0 otherwise. We mask out all other bits to 0s. In sum,
the delimiters bitmap is derived as
\begin{center}
    delimiters $=$ extensions \& $($extensions >‌> 1$)$ \& $0101\dots0101$.
\end{center}
Finally, we use the select operation to
evaluate~$\texttt{select}(m,$~delimiters$)$, which skips over the first~$m$
delimiters and returns the position of the~$m${\nobreakdash-}th delimiter. We
sequentially apply the bitwise operations above to each machine word comprising
the chunk's extensions. This is efficient, as a chunk's extensions often fit in
1-2 words.

\Cref{fig:extension_location_example} shows an example of locating the 3rd
counter's extension using rank and select. Here,
$\texttt{rank}(3,$~overflows$)=1$. Thus, after deriving the delimiters bitmap
by manipulating the extension pool, \sketchcms
evaluates~$\texttt{select}(1,$~delimiters$)=9$ to conclude that the target
extension ends at the~9th bit.

\textbf{Tails.}
In the rare event that many hot keys hash to the same chunk, many of the
chunk's counters will overflow, potentially growing the cumulative length of
the extensions beyond the size of the chunk. \sketchcms handles this case by
allocating an external array of 32-bit integers called \emph{Tails} for the
chunk, with one tail integer per counter. It stores the~$i${\nobreakdash-}th
counter's higher-order bits in the~$i${\nobreakdash-}th tail. Each chunk
contains a mode flag indicating if it has a tails array, as depicted in
\Cref{fig:counter_chunk_with_tails}. If it does, we repurpose the space taken
up by the extension pool to store a pointer to the tails array. We ensure that
the extension pool is large enough to accommodate this pointer (i.e., at least
48 bits\footnote{The upper 16 bits a general 64-bit pointer are unused on
modern machines. As such, we only store the lower 48 bits of the pointer.})
when tuning the number of counters per chunk~$c$ and the stub size~$s$. Any
extra space after the pointer is left unused.

In the next subsection, we show that adaptively tuning the number of counters
per chunk~$c$ and the stub length~$s$ ensures extensions rarely outgrow their
chunks. This drastically reduces the number of tails arrays, making their
memory overhead negligible.

\textbf{Incrementing Counters.}
When an insertion maps to the~$i${\nobreakdash-}th counter of a chunk,
\sketchcms increments it by adding one to the lower-order bits stored in
the~$i${\nobreakdash-}th stub, i.e., stub[$i$]. Most of the time, stub[$i$]'s
increment will not carry over to the higher-order bits of the counter, allowing
the insertion to return early and achieve high throughput. 

Whenever stub[$i$]'s increment carries over, \sketchcms adds one to the
counter's extension or tail. For an extension, this entails incrementing its
first digit and propagating a carry to the other digits as necessary. This
carry may propagate beyond the end of the extension, leading to the addition of
a new digit. \sketchcms makes room for the fragment representing this digit by
shifting subsequent extensions to the right. If the~$i${\nobreakdash-}th
counter did not have an extension, a new extension encoding the value~1 is
created for it. We use rank and select operations to determine the appropriate
position of this extension in the extension pool.

\textbf{Decrementing Counters.}
Analogously, when a deletion maps to the~$i${\nobreakdash-}th counter in a
chunk, \sketchcms decrements the lower-order bits in~stub[$i$]. If stub[$i$]
borrows from the counter's higher-order bits as a result, \sketchcms decrements
the corresponding extension or tail. This may trigger the removal of a digit
from the counter's extension, in which case subsequent extensions are shifted
to the left to keep the extension pool tightly packed. 

\textbf{Optimization~1: Fast Division.}
Determining the chunk of a counter at offset~$i$ in an array is expensive, as
it entails dividing~$i$ by the number of counters per chunk~$c$, which may not
be a power of two. We avoid this cost by simulating the division through
fixed-point multiplication. Specifically, we compute the
expression~$\left\lfloor \left(i/2^{\lceil \log_2 c \rceil}\right) \cdot
\left(2^{\lceil \log_2 c \rceil}/c\right) \right\rfloor = \left\lfloor i/c
\right\rfloor$ by representing the multiplicands as fixed-point fractional
numbers. To this end, we precompute the latter multiplicand's fixed-point
representation with~$\left\lceil \log_2 w \right\rceil$ bits of precision,
where~$w$ is the size of an array. For the former multiplicand, we treat~$i$'s
binary representation as a fixed-point fractional value with the decimal point
being after the~$\left\lceil \log_2 c \right\rceil${\nobreakdash-}th bit.
Finally, we multiply these values using standard integer multiplication and
shift the result~$\left\lceil \log_2 w \right\rceil + \left\lceil \log_2 c
\right\rceil$ bits to the right to remove the fractional bits and compute the
answer.

\textbf{Optimization~2: Hardware Accelerated Rank and Select.}
\sketchcms utilizes specialized CPU instructions to implement rank and select
operations. It implements~$\texttt{rank}(i,B)$ by applying the \verb|POPCNT|
instruction to the first~$\left\lceil i/64 \right\rceil$ words of the
bitmap~$B$ to count the~1s before the~$i${\nobreakdash-}th
bit.\footnote{Formally, denoting the~$j${\nobreakdash-}th word in~$B$ as~$B_j$,
this process corresponds to computing \texttt{POPCNT}$ \left(B_{\lfloor i/64
\rfloor}\text{~\&~}((1 \text{ <‌< } (i \mod 64))-1) \right) +
\sum_{j=0}^{\lfloor i/64 \rfloor -1}$ \texttt{POPCNT}$(B_j)$.} It also
implements~$\texttt{select}(i,B)$ by counting the 1s
in~$B$'s words to locate the word containing the $i${\nobreakdash-}th~1. Once
found, it applies the x86 instructions \verb|PDEP| and \verb|TZCNT| to evaluate
the target bit's position within that word, as described in
\cite{GQF}.\footnote{If the~$j${\nobreakdash-}th word $B_j$ contains
the~$i${\nobreakdash-}th 1 and there are~$r$ 1s in the preceding words, the
result is computed as~$64 \cdot j + $\texttt{TZCNT}$($\texttt{PDEP}$((1 \text{
<‌< } (i-r)) - 1, B_j))$, where the first operand of \texttt{PDEP} is the
payload and the second operand is the mask~\cite{PDEP}.} Each of these commands
is applied to 1-2 machine words, as the bitmaps \sketchcms operates over are
1-2 words long.

\textbf{Optimization~3: Lookup Tables.}
Since stubs are not byte-aligned, modifying them can be costly. This is because
extracting and writing back a stub to the machine words containing it entails
five extra bitwise operations on top of the addition operation. \sketchcms
bypasses this cost by directly updating the stub's words using a single
addition. It achieves this using two precomputed lookup tables. The first table
stores the position of the word each stub lies in, and the second table stores
the stub's position within its word. \sketchcms updates a stub by adding or
subtracting one from the bit indicated by the second table in the word
indicated by the first. For example, in the context of
\Cref{fig:counter_chunk}, the first lookup table indicates that the~1st stub
lies in the 1st word, which has a binary representation of~$111111101010\dots$.
The second lookup table indicates that this stub starts at the~6th bit in the
1st word, allowing us to increment it by adding~$000000100000\dots$, thus
yielding the updated word~$111111011010\dots$.

\textbf{Optimization~4: Prefetching.}
We allow multiple chunks to be read in parallel within a single operation as
well as across multiple operations using prefetching techniques similar to that
of~\cite{StingySketch}. Specifically, we maintain a prefetching queue for each
array in \sketchcms that records the eight most recent requests for chunks.
Each time a chunk is requested from an array, a software prefetch instruction
is issued for it, and the request is pushed into the array's queue. When a
queue fills up, the chunk of its oldest request will be present in the L1
cache, allowing it to be read efficiently while other chunks are being loaded
into the cache. 

\textbf{Optimization~5: Hash Splicing.}
Recall that a key is hashed into each of the sketch's~$d$ arrays during an
update or query. Instead of applying~$d$ separate hash functions and incurring
their CPU overheads, \sketchcms applies a single hash function to the key to
compute a long hash. It splices the result into~$d$ sub-hashes of equal length
and uses each as the hash value of an array. 

\subsection{Accommodating Unknown Stream Lengths}\label{sec:accommodating_unknown_stream_lengths}
\sketchcms generalizes CMS to handle streams of unknown length by maintaining a
chain of sketches. Each sketch in the chain consists of~$d$ counter arrays,
each of which is twice as large as the arrays of the preceding sketch in the
chain. \Cref{fig:sketchbook_chain} illustrates this chain. \sketchcms directs
insertions and deletions to the last sketch in the chain so that they benefit
from its higher tracking accuracy. It expands and contracts as the stream
evolves by adding and removing sketches from the chain, respectively. It does
so to keep the size of the last sketch's counter arrays close to the value of a
user-defined \emph{Size Function}~$w^*(N)$, which is an increasing function of
the current total number of keys in the stream~$N$. This simulates processing
the stream with a sketch preallocated from the onset with arrays of
size~$w^*(N)$, yielding a similar accuracy guarantee with almost the same
memory footprint.

Although insertions and deletions only modify the last sketch, queries must
consult all sketches in the chain to aggregate their estimates, and are thus
slower. \sketchcms addresses this issue by aggregating the updates of all
sketches into the last one, allowing queries to probe the last sketch only. The
memory footprint of the chain is domniated by the last sketch, which takes up
at least half of the space.

\textbf{Size Function.} 
The size function~$w^*(N)$ controls an accuracy-memory tradeoff: the
faster~$w^*(N)$ grows with respect to the total number of keys in the
stream~$N$, the sooner \sketchcms expands. As such, it tracks more of the
stream's keys at a higher accuracy in exchange for a higher memory footprint.
We recommend using a size function of the form~$w^*(N)=N^\alpha/\epsilon$ and
tuning the constants~$\alpha \in [0,1)$ and $\epsilon$ to balance accuracy with
memory. Such a size function is known as a \emph{Sub-Linear Power}. We prove in
\Cref{sec:theoretical_analysis} that using a sub-linear power yields an error
bound of~$O(N/w^*(N))=O(\epsilon \cdot N^{1-\alpha})$. This matches the error
bound of a sketch preallocated with arrays of size~$w^*(N)$ with a similar
memory footprint, which is known to be optimal~\cite{CountMin}.

One might expect to achieve an error bound of~$O(\epsilon)$ to by
setting~$w^*(N)=N/\epsilon$. Yet, in \Cref{sec:theoretical_analysis}, we show
that the best error bound achievable by a sketch with~$O(N/\epsilon)$ counters
without knowing the ultimate length of the stream is~$O(\epsilon \cdot \log
N)$. Moreover, we show that \sketchcms attains this error bound under the same
memory budget and is therefore optimal.

\textbf{Expansions.} 
Whenever~$N$ increases enough to double the value of the size
function~$w^*(N)$, \sketchcms expands by adding a new sketch to the chain with
counter arrays twice as large as that of the old last sketch. Doing so ensures
that the last sketch's counter arrays always have a size in the
range~$[w^*(N)/2,w^*(N)]$, as depicted in \Cref{fig:sketchbook_chain}.

When using a sub-linear power as the size function, triggering an expansion
requires inserting the majority of the stream's keys into the last
sketch.\footnote{More generally, this holds when~$w^*(N)$ is an increasing
concave function of~$N$.} As such, the error resulting from the last sketch is
the dominant factor in the overall error bound of \sketchcms. Since this sketch
has an error of approximately~$N/w^*(N)$, this yields an overall error
of~$O(N/w^*(N))$, as we prove in \Cref{sec:theoretical_analysis}.

\textbf{Contractions.} 
Whenever deletions decrease~$N$ enough to halve the value of the size
function~$w^*(N)$, \sketchcms contracts to save memory. It does so by
transferring the updates of the last sketch to the penultimate sketch and
discarding the last sketch. This information transfer is challenging, as the
keys are not stored in the sketches, barring us from rehashing them into the
penultimate sketch. We overcome this issue by using a fixed set of~$d$ hash
functions~$h_1,\dots,h_d$, one for each array in all of the sketches. That is,
we hash a key~$x$ to a counter in the~$i${\nobreakdash-}th array of a sketch by
computing~$h_i(x)$ to derive a long hash. Letting~$w$ be the size of this
array, we take the~$\log_2 w$ lower-order bits of~$x$'s hash to map it to its
counter. \Cref{fig:contraction} shows this procedure for the last two sketches
in the chain.

This hashing scheme allows \sketchcms to determine the counter a key hashes to
in the penultimate sketch by removing the most significant bit (MSB) of its
counter's offset in the last sketch. For example, considering the first array
of the last sketch in \Cref{fig:contraction}, all keys such as key~$x$ that
have~1101 as the lower-order bits of their hash are hashed to the~11th counter.
Removing the MSB of this counter's offset yields~110, implying that all those
keys, including~$x$, hash to the~3rd counter in the first array of the
penultimate sketch. Thus, adding the value of a counter in the last sketch to
its corresponding counter in the penultimate sketch transfers the effects of
all updates that hashed to it. Since the MSB of the counters' offsets
partitions the last sketch into two halves, transferring all of its updates
amounts to adding each partition to the penultimate sketch.

As in the case of expansions, when using a sub-linear power as the size
function, the majority of the stream's keys must be deleted to trigger a
contraction. This amortizes the contraction cost, and, as we prove in
\Cref{sec:theoretical_analysis}, ensures that the last two sketches of the
chain always track the majority of the keys in the stream. Therefore, the error
bound is controlled as before, despite the state of each particular sketch in
the chain depending on the sequence of insertions and deletions done.

\textbf{Aggregating Sketches.}
Although insertions and deletions only modify the last sketch, queries must
aggregate the estimates of all sketches in the chain, and are thus slower.
\sketchcms addresses this issue by aggregating the updates of all older
sketches into the last one, allowing queries to probe the last sketch only. As
in the case of contractions, we achieve this by leveraging the fixed set of
hash functions used for all sketches. Specifically, we add the value of each
counter in an older sketch to all counters in the last sketch with offsets
whose lower-order bits match that of the old counter.
\Cref{fig:aggregating_sketches} illustrates this for the~3rd counter in the
first array of an older sketch. Here, the offsets~3, 7, 11, and 15 all have~11
as their lower-order bits, thus matching the old counter's offset. We therefore
add the value of the old counter to the counters at these offsets. This allows
any query~$x$ that hashes to these counters to take into account the value of
the~3rd counter in the old sketch without needing to directly query it.
Applying this procedure to all counters in the old sketch amounts to
partitioning the counters of the last sketch based on their counters' MSBs and
adding the old sketch to each partition.

The aggregation procedure above does not cause data loss, 
Subtracting away the old sketches from the aggregated last sketch in the same
way yields the original last sketch. 

\textbf{Storing the Aggregated Sketch Only.}
Contractions never occur when the keys are only inserted into the stream. When
handling such streams, \sketchcms exploits this to save memory by discarding
the old sketches of the chain and only keeping the aggregate sketch, as old
sketches are only required for handling contractions. Here, expansions amount
to creating a larger aggregate sketch by concatenating the aggregate sketch
with a duplicate of itself.

\subsection{Generalization to Count Sketch}\label{sec:cs}
%For example, in join size estimation, multiplying overestimated counts from the input tables leads to an overly large join size.

\textbf{Count Sketch (CS).}
CMS has two key shortcomings: (1)~its estimations are biased since it only
overestimates and (2)~its errors compound when it is used in some tasks,
particularly those that multiply frequencies. One cannot discount CMS's
estimates to eliminate their bias, as the correction amount varies from key to
key and depends on the ground-truth frequency. CS addresses these issues by
providing unbiased estimates. The third row of
\Cref{tab:classical_sketch_stats} summarizes the properties of CS and compares
it to CMS.

The core component of CS is a counter array of size~$w$ coupled with a hash
function~$h_i$ mapping a key to a counter. CS further associates with each key
a random ``update direction'' from the set~$\{-1,+1\}$ by hashing it with
another hash function~$\sigma_i$.\footnote{The~$\sigma_i$ form a 4-wise
independent family of hash functions, yielding a bound on the probability of
large errors~\cite{CountSketch}.} It inserts a new key~$x$ by incrementing or
decrementing its counter according to~$\sigma_i$, as shown in
\Cref{fig:cs_overview}. CS deletes~$x$ by subtracting~$\sigma_i(x)$ from its
counter to undo its insertion. Since each key's update direction is random, the
expected interference on~$x$'s counter from any other key is zero due to the
positive and negative possibilities canceling out. Thus, the value of the
counter along the update direction is an estimate of~$x$'s frequency, which CS
returns during a query. Although this estimate may be smaller or larger than
the ground-truth frequency, the zero expected interference allows it to match
the ground-truth on average, removing bias. Increasing the array's size reduces
the likelihood of hash collisions and the average deviation.

the same counter, degrading confidence. CS addresses this by employing~$d$
independent arrays, each with its own hash functions~$h_i$ and $\sigma_i$.

may greatly underestimate the result due to two-sided errors. Instead, it
returns the median estimate, as shown in \Cref{fig:cs_overview}. This improves
confidence since severe errors are unlikely to occur for enough experiments to
affect the median. CS takes the median instead of the mean to improve
robustness to outlier estimates. With~$d$ arrays with~$w$ counters each, CS
guarantees an error bound of at most~$\sqrt{\frac{e \cdot \sum_{y}
(f(y))^2}{w}}$ with a confidence of~$1-e^{-d}$, i.e., $\Pr\left(
|\hat{f}(x)-f(x)| \leq \sqrt{\frac{e \cdot \sum_{y} (f(y))^2}{w}} \right) \geq
1-e^{-d}$ for any key~$x$. The error term above is smaller than CMS's error
term when the frequency distribution is less skewed, as the root slows its
growth to~$O(\sqrt{N})$ (vs.~$N$) when the summands are small.

\Cref{fig:mg_overview} presents an overview of MG. MG maintains an array of
slots, each storing a key (shown in gray) and a dedicated frequency counter
(shown in white). MG estimates the frequency of each key in the array as the
value of its counter. It returns an estimate of zero for the untracked keys.
When inserting a key~$x$, MG first checks if it has a dedicated counter in some
slot. If it does, MG increments~$x$'s counter. If not, and the array has an
empty slot, MG stores~$x$ in it with a count of~$1$. If~$x$ is not in the array
and the array is full, MG decrements all counters and discards any keys whose
counters become zero. Such keys are unlikely to be among the most frequent and
their slots are better used for tracking hotter keys. Note that~$x$ is not
stored in the newly emptied slots and is only stored if it is inserted when
some slot is already empty. MG does not support deletions. This is because it
lacks information about the untracked keys, which may become hot after the
currently hot keys are deleted, thereby failing to place them in its array.

Having more slots in the array allows MG to track more keys without discarding
them, leading to more accurate estimates. Since MG is a deterministic data
structure that does not use hashing, unlike CMS and CS, it does not suffer from
hash collisions, and its estimations have full confidence. Using an array
of~$w$ slots, MG estimates the frequency of any key with an error of at
most~$\frac{N}{w}$, i.e., $|\hat{f}(x)-f(x)| \leq \frac{N}{w}$ for any key~$x$.
Since it uses dedicated counters for the hot keys, it also provides a strong
``\emph{Tail Guarantee},'' stating that the error for any key is at
most~$\min_{1 \leq i \leq w} \frac{N^{\text{res}(i)}}{w-i+1}$, where
$N^{\text{res}(i)}$ is the total frequency of all keys not among the top~$i$.
Note that~$N^{\text{res}(i)}$ is much smaller than~$N$ when the data is skewed.

Since MG only increments a key's counter if it is in the array and decrements
counters otherwise, it only underestimates frequencies. Thus, its estimates are
biased. For similar reasons to CMS, this bias cannot be removed by enlarging
estimates. Yet, probabilistically replacing the array's least frequent keys can
yield unbiased estimates~\cite{UnbiasedSpaceSaving}. Other variations of MG
achieve higher accuracy in practice, but suffer from two-sided errors in
exchange~\cite{SpaceSaving}.

Typical implementations of MG use a hash table to implement the array of keys,
yielding constant-time queries. They also optimize insertions by lazily
decrementing the counters and employing an auxiliary heap to locate and discard
keys with zero counts.

\section{Theoretical Analysis}\label{sec:theoretical_analysis}
We prove in~\Cref{sec:theoretical_analysis} that Sketchbook maintains its
confidence without varying the number of arrays. One can also expand the number
of arrays to improve confidence over time. We omit this from our exposition due
to its similarity to the approach of expanding the number of counters in each
array.
