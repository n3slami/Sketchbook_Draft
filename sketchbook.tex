\section{Introduction}~\label{sec:introduction}
We define the following two goals: \textbf{(G1)~Space-Efficient Counters}, and
\textbf{(G2)~Scaling Error with Stream Length}.

\textbf{Applications.} 
Due to its simplicity and high accuracy under skewed workloads, CMS is used in
many applications, including $k$-mer counting in
bioinformatics~\cite{CMSkmer,SetMinSketch}, network
monitoring~\cite{SketchBasedChangeDetection,WhatsNew,TrafficManagementSurvey},
and hardware security systems~\cite{CoMeT}. Yet, its biased estimates make it
less useful for applications such as join size estimation. As shown in
\Cref{sec:cs}, the Count Sketch is the tool of choice for these settings.

Since CS provides unbiased estimates, it is used in applications where
estimates are combined or multiplied to derive more complex statistics. In
particular, unbiased estimation is crucial for query
optimization~\cite{Compass,QueryOptimizationSketches,ConvolutionSketch} and
covariance estimation~\cite{ASCS}, as frequency estimates are multiplied in
these contexts, amplifying any bias. Other applications benefiting from CS
include feature selection~\cite{MISSION} and similarity
search~\cite{CSSetSimSearch,DensifyingLSHSketches,LasVegasSimSearch,DistanceSensitiveBloomFilters}.
CS also provides \emph{Universality}~\cite{UniversalSketching}: the ability to
estimate many statistics based on the key frequencies. This makes it a general
measurement tool for networks since it allows administrators to collect
diagnostics of any kind without needing to explicitly define the required
statistics (such as the mean, variance, and moments) beforehand~\cite{UnivMon}.

As MG accurately tracks the frequencies of hot keys, many other sketch designs
use it as a sub-component to reap its benefits. Moreover, because it also
stores the keys themselves, unlike CMS and CS, it is used to report the hottest
keys, trending keys, and much
more~\cite{BatchUpdateMisraGries,AugmentedSketch,BitMatcher,BubbleSketch,HeavyGuardian,HeavyKeeper,JigsawSketch,MVSketch,SketchVisor,WavingSketch,MicroscopeSketch,PSketch,TightSketch}.

\section{Background}~\label{sec:background}
The simplest approach to tracking the frequency of keys in a stream is to store
each key and its count in a hash table. Although this solution provides an
accurate count of each key's frequency, it entails high memory overheads for
multiple reasons: 1)~It stores all keys in the stream, incurring a linear
memory footprint. This overhead worsens if the keys are variable-length, as
they require a layer of indirection such as pointers for storage. 2)~It stores
one counter for each key. 3)~Each counter must be long enough to accommodate
the maximum count, even if most keys have a very low count. 4)~The hash table
may have a space utilization as low as 50\% to support collision resolution and
expansions. These overheads multiply with the number of streams the application
monitors. The Count-Min Sketch (CMS) addresses problems~1, 2, and 4 by trading
accuracy for space, though it slightly worsens problem~3. In
Sections~\ref{sec:cs} and \ref{sec:mg}, we discuss alternatives to CMS such as
Count Sketch and Misra-Gries and apply our techniques to them.

\textbf{Streams and Frequency Estimation.}
We consider a stream model where keys are both inserted and deleted, which
amount to incrementing and decrementing the key's frequency, respectively.
while some applications such as tracking click-through rates in webpages only
require insertions, deletions are needed for other applications such as
maintaining frequency estimates for SQL tables for use in a query optimizer.
Formally, a stream is a sequence of key and update operation
pairs~$\left\langle (x_1,\Delta_1), (x_2,\Delta_2), \dots, \right\rangle$,
where each~$x_i$ is a key and~$\Delta_i = \pm1$ represents whether its
frequency was incremented ($\Delta_i=1$) or decremented ($\Delta_i=-1$). This
is known as the \emph{General Turnstile Model} of data
streams~\cite{StreamModels}. At any point, $N=\sum_i \Delta_i$ represents the
total number of keys. Given a data stream a frequency estimation sketch
provides, for any key~$x$, an estimate~$\hat{f}(x)$ of the number of
times~$f(x)$ it has appeared in the stream.
\Cref{tab:term_and_symbol_definitions} lists the terms and symbols used
throughout the paper.

\textbf{CMS.}
The core design element of CMS is an array of~$w$ counters, initialized to
zeros. CMS inserts a key~$x$ by mapping it to a counter in the array using a
hash function and incrementing the counter. It deletes~$x$ by decrementing its
counter. CMS estimates the frequency of~$x$ as the counter value it hashes to.
The top row of \Cref{fig:cms_overview} shows an example of this array along
with an insertion and a query. Due to hash collisions, multiple keys can map to
the same counter. Because of this, the in this array may overestimate
frequencies. Increasing the array's size makes hash collisions less likely and
improves CMS's \emph{Accuracy}.

Yet, no matter the array's size, all keys sharing the same counter as a
frequent key will suffer from heavily inflated estimates. Such collisions
reduce CMS's \emph{Confidence} in its results. CMS counteracts this by
allocating~$d$ independent counter arrays, each with a dedicated hash
function~$h_i$. CMS inserts or deletes a key by applying the operation to each
array, and answers a query by querying all arrays and taking the minimum
estimate.\footnote{CMS ensures a reduction in estimation error by employing
pairwise-independent hash functions. Doing so bounds the probability of
collisions and overestimation~\cite{CountMin}.} \Cref{fig:cms_overview} shows
an example of insertions and queries. Returning the minimum for queries
improves confidence since it only carries severe errors when all estimates err
significantly. As such, CMS ensures an error bound of at most~$\frac{eN}{w}$
with a confidence of~$1-e^{-d}$, i.e., $\Pr\left( |\hat{f}(x)-f(x)| \leq
\frac{eN}{w} \right) \geq 1-e^{-d}$ for any key~$x$.

\textbf{Tradeoffs.}
CMS avoids storing the stream's keys and only uses a constant number of
counters that are tightly packed to remove unused space. As such, its memory
footprint is significantly smaller than the hash table approach. In exchange,
its estimations are biased since it only overestimates. Moreover, CMS's errors
compound when the sketch is used in some tasks, particularly those that
multiply frequencies. One cannot discount the estimates to eliminate their
bias, as the correction amount varies from key to key and depends on the
ground-truth frequency. In \Cref{sec:cs}, we describe the Count Sketch and show
how it achieves unbiased estimation.

\section{Problem Analysis}\label{sec:problem_analysis}
This section highlights the challenges CMS faces in achieving the two goals
outlined in~\Cref{sec:introduction}, as well as the limitations of existing
approaches to improving CMS.
%Describe how many sketches allocate fixed-length counters to count the items. Since the counters are fixed-length, they must all be large enough to accommodate tha maximum count. As such, many counters will not use their higher-order bits, wasting memory. 

\textbf{Space-Efficient Counters~(G1) and Accuracy.}
CMS uses fixed-length counters in its arrays. Each counter must be at
least~$\log_2 N$ bits long to avoid overflowing, as it can become as large
as~$N$ in the worst case when all of the stream's keys map to it. Yet, since
hashing spreads the keys uniformly across the counters, most counters will be
small, leaving many of their bits unused. Ideally, each counter should be just
long enough to fit its value; i.e., the counters must be variable-length. This
allows CMS to have more counters under the same memory budget and achieve
higher accuracy. 

CMS requires additional metadata to locate the beginning and end of
variable-length counters. The challenge is to minimize the amount of metadata
to improve space efficiency. In practice, one can only afford~$\approx 1$ bit
of metadata per counter. This is because many counter values never exceed 127
in realistic configurations~\cite{StingySketch} and thus fit in at most 7 bits,
implying that having 2 metadata bits per counter translates to a memory
overhead of at least~$\approx 30\%$.

\textbf{Pitfall of Supporting~(G1): Counter Sharing.} 
Many sketches achieve~(G1) by using short counters and storing the overflows in
``shared'' pieces of memory. For example, \cite{SALSA} merges an overflowing
counter with its adjacent counter to create a longer counter storing their
aggregate value. Other
sketches~\cite{BitSense,PyramidSketch,StingySketch,AdaptiveCounterSplicing,CounterTree,TreeSensing}
allocate a small number of counter fragments, each acting as the higher-order
bits of multiple short counters. A counter's value is retrieved by
concatenating its fragments. Counter sharing negatively impacts accuracy, as it
blows up many otherwise small counters. Sketchbook attains~(G1) without counter
sharing, avoiding the drop in accuracy.

Moreover, counter sharing couples the counter values together, altering their
statistical behavior. This complicates the integration of other orthogonal
techniques, such as using Bayesian inference for improving
accuracy~\cite{BayesianSketches} and applying the convolution operator for
join-size estimation~\cite{ConvolutionSketch}. By avoiding counter sharing,
Sketchbook allows for seamless integration of these techniques.

\textbf{Handling Streams of Unknown Length~(G2).}
In many applications, such as counting SQL table entries or tracking network
activity in a fixed time interval, the number of keys in the stream~$N$ is
unknown. Since the error of CMS (and other sketches) scales linearly with~$N$,
the value of which is hard to predict, practitioners are faced with the
challenge of tuning the sketch's size to control the error. If the sketch is
too small, the estimates will have significant errors, and if it is too large,
memory is wasted. Sketchbook overcomes this challenge by expanding along with
the stream, minimizing memory wastage, and achieving sub-linear errors.

\textbf{Maintaining High Performance.} 
While variable-length counters significantly reduce memory consumption~(G1),
accessing and updating them is costly. This stems from the counters no longer
being word-aligned and requiring extra logic to parse. The parsing overhead is
even higher in methods that compute a highly compressed sketch and decompress
it to answer queries. These methods are unsuitable for online query processing,
as the decompression algorithm typically entails heavy-weight algorithms such
as compressive sensing~\cite{TreeSensing,BitSense} and hyper-graph
peeling~\cite{CodingSketch}, limiting their applicability. Sketchbook achieves
high performance by avoiding expensive decompression algorithms, ensuring that
each counter is fully contained within a single cache line, prefetching these
cache lines, and employing lookup tables and specialized CPU instructions to
manipulate them efficiently.

Handling unknown stream lengths~(G2) introduces additional overheads, as
updates must also expand CMS. It may also adversely impact queries, as they
must probe a more complex structure. Minimizing these performance overheads is
critical for many applications, such as network monitoring, where CMS must
process packets at line
speed~\cite{SketchBasedChangeDetection,WhatsNew,TrafficManagementSurvey}.
Sketchbook addresses this problem by leveraging SIMD to optimize expansions and
by maintaining a read-optimized sketch to speed up queries.

\textbf{Supporting Deletes.}
Deletions reduce the number of keys in the stream~$N$, improving CMS's
accuracy. Yet, if~$N$ drops disproportionally to the memory budget, CMS's
overly large memory yields diminishing returns in accuracy. To address this
issue and attain~(G2) while maintaining space efficiency and accuracy, the
sketch must contract. Moreover, to meet~(G1), each counter in the sketch must
handle deletions gracefully, shortening whenever possible to allow for more
counters and improve accuracy. This is particularly challenging for methods
using counter sharing, as it is unclear how to ``separate'' the counters once
they become small.

\textbf{Summary.}
Although much research has gone into achieving space-efficient counters~(G1),
existing sketches either 1)~use counter sharing and thus inherit its downsides,
2)~are inefficient, or 3)~do not support deletes. Moreover, no work explores
the idea of expanding sketches to handle streams of unknown length~(G2). Is it
possible to design a sketch that achieves~(G1) and (G2) while maintaining high
performance and supporting deletes?

\section{Sketchbook}\label{sec:sketchbook} 
We present Sketchbook, a general framework for memory-efficient frequency
estimation using variable-length counters and expansions.
\Cref{sec:expanding_counters} describes how Sketchbook employs techniques
inspired by linear probing~\cite{LinearProbing,RobinHoodHashing} to encode
variable-length counters. Each of these counters grows to the appropriate size
for its value while minimizing metadata overhead. We also describe how
Sketchbook uses rank and select primitives and lookup tables to maintain this
encoding efficiently. \Cref{sec:expanding_columns} describes how Sketchbook
expands the entire structure to handle streams of unknown lengths, yielding
better error guarantees. Specifically, Sketchbook utilizes an \emph{Expansion
Rate Function}, which is a function of the stream's length, and expands
whenever its value doubles. The faster this function grows, the earlier the
sketch expands and the more accurate it becomes, exposing an accuracy-space
tradeoff. Expansions enable Sketchbook to achieve memory efficiency in exchange
for slightly slower amortized updates. Moreover, Sketchbook supports deletions
and contractions with a small overhead in memory. We show
in~\Cref{sec:theoretical_analysis} that there is no merit in expanding the
number of rows and thus omit it from our discussion. For concreteness, we
describe our techniques applied to CMS as a running example and generalize them
to other sketches in Sections~\ref{sec:cs} and \ref{sec:mg}.

\subsection{Expanding Counters}\label{sec:expanding_counters}

and 2-bit extensions allows us to fit the encoding of these 64 counters neatly
into a 512-bit cache line, yielding good cache behavior.

\textbf{Stub Counters Array.} 
Given a logical array of counters, Sketchbook encodes it by first allocating an
array of small, $b$-bit counters to each. Each stub counter encodes the~$b$
least-significant bits of its logical counter. Here, $b$ is a tuning parameter
denoting the width we expect each counter to be. We have found~$b=6$ is
reasonable for many sketch configurations. As the some logical counters can
grow beyond the range of~$b$-bit counters, we require another mechanism to
succinctly encode the remaining higher-order bits of these counters.

\textbf{Overflowed Bitmap.} 
To this end, we employ a contiguous overflowed bitmap to indicate which stub 
counters have reached their limit and have overflowed. For any overflowed
counter, we encode the remaining higher-order bits using~$b'$-bit extensions.

\textbf{Extensions Array.}
Explain that the~$b'$-bit extensions represent the value of the counter's
higher-order bits in base-$(2^{b'}-1)$. Explain that we pack all extensions
contiguously into an extensions array, forming runs. State that we reserved one
of the~$2^{b'}$ values to act as a delimiter between the runs. Give a sense of
the total space overhead one can expect for the average counter.

\textbf{Locating a Run.}
Introduce rank and select and state that we apply them along with some bitwise
operations to the extensions array to locate the end of a run.

\textbf{Decoding Counters.}
Explain how we decode a counter given the encoding above.

\textbf{Spill Mechanism.} 
In unlikely scenarios, the extensions array may fill up and make the sketch run
out of space. Inspired by frontyard/backyard hash table designs, we implement a
``spill'' mechanism that activates when the extensions array fills up. Here, we
employ a flag in the extensions array to denote whether we are in the spilled
state. If we are, the extensions array stores a pointer to an array of full
counters, which will now store the values of the counters, modulo the $b$
least-significant bits already stored in the stub counters. We expect the
memory overhead of the spill mechanism to be very small, as it is only
activated in the unlikely even of the extensions array filling up.

the expansion function doubles. Give intuition about how this maintains
approximately~$C(N)$ columns/slots at any point in time with the hope of
achieving the same behavior as a sketch of size~$C(N)$ allocated with knowledge
of~$N$. Doing so controls the total error as the sum of a geometric series.

\textbf{Aggregating Sketches.}
Having to work with the entire chain and to query all sketches in it is slow.
To avoid this cost, we create an aggregate sketch that takes into account all
sketches in the chain. Explain the sketch doubling method for CMS and CS and
that it allows us to keep using the same hash function across time. To save
memory and avoid storing the aggregate sketch as well, we ``replace'' the last
sketch in the chain with the aggregate sketch. Argue that this does not create
information loss, as we reconstruct the last sketch by ``subtracting out'' the
old ones. 

Point out that for MG, as it doesn't use hashing and is more of an associative
array, we expand on a slot-by-slot basis to exactly match~$C(N)$, yielding
potentially higher accuracy. 

\textbf{Contractions.} 
Explain that we have to shrink the sketch to save memory if too many keys are
deleted. Specifically, when the expansion rate function is halved, we
reconstruct the final sketch in the chain by ``subtracting out'' the other
sketches from the aggregate sketch. As a result of this subtraction, some
counters may be positive, signifying inserts, and some may become negative,
signifying deletes. As such, it behaves like an ``update sketch,'' which
``fold'' onto itself to make it the same size as the previous sketch in the
chain and add them to propagate back the updates. 

Give intuition that the error bound remains good, as the old sketches contain a
small fraction of keys, and a lot of keys must be deleted for a contraction to
occur. Also point out that now, the state of the sketches in the chain depends
on the sequence of inserts and deletes done. Regardless of the sequence,
however, the error bounds hold.

\textbf{Physical Storage.}
If we only want to support inserts, we physically manifest only the aggregate
sketch to save memory. For deletes, since we have to subtract out the old
sketches during contractions to reconstruct the final chain sketch, we need to
store the entire chain.

\subsection{Generalization to Count Sketch}\label{sec:cs}
\textbf{Count Sketch (CS).}
Unlike CMS, CS provides unbiased estimates of a key's frequency. The third row
of \Cref{tab:classical_sketch_stats} summarizes the properties of CS and
compares it to CMS.

The core component of CS is an array of~$w$ counters coupled with a hash
function~$h_i$ mapping a key to a counter. CS further associates with each key
a random ``update direction'' from the set~$\{-1,+1\}$ by hashing it with
another hash function~$\sigma_i$.\footnote{The~$\sigma_i$ form a 4-wise
independent family of hash functions, yielding a bound on the probability of
large errors~\cite{CountSketch}.} It inserts a new key~$x$ by incrementing or
decrementing its counter according to~$\sigma_i$, as shown in
\Cref{fig:cs_overview}. CS deletes~$x$ by subtracting~$\sigma_i(x)$ from its
counter to undo its insertion. Since each key's update direction is random, the
expected interference on~$x$'s counter from any other key is zero due to the
positive and negative possibilities canceling out. Thus, the value of the
counter along the update direction is an estimate of~$x$'s frequency, which CS
returns during a query. Although this estimate may be smaller or larger than
the ground-truth frequency, the zero expected interference allows it to match
the ground-truth on average, removing bias. Increasing the array's size reduces
the likelihood of hash collisions and the average deviation.

As with CMS, a frequent key will adversely impact the estimates of keys sharing
the same counter, degrading confidence. CS addresses this by employing~$d$
independent arrays, each with its own hash functions~$h_i$ and $\sigma_i$.
Unlike CMS, CS cannot answer a query by returning the minimum estimate, as it
may greatly underestimate the result due to two-sided errors. Instead, it
returns the median estimate, as shown in \Cref{fig:cs_overview}. This improves
confidence since severe errors are unlikely to occur for enough experiments to
affect the median. CS takes the median instead of the mean to improve
robustness to outlier estimates. With~$d$ arrays with~$w$ counters each, CS
guarantees an error bound of at most~$\sqrt{\frac{e \cdot \sum_{y}
(f(y))^2}{w}}$ with a confidence of~$1-e^{-d}$, i.e., $\Pr\left(
|\hat{f}(x)-f(x)| \leq \sqrt{\frac{e \cdot \sum_{y} (f(y))^2}{w}} \right) \geq
1-e^{-d}$ for any key~$x$. The error term above is smaller than CMS's error
term when the frequency distribution is less skewed, as the root slows its
growth to~$O(\sqrt{N})$ (vs.~$N$) when the summands are small.

\Cref{fig:mg_overview} presents an overview of MG. MG maintains an array of
slots, each storing a key (shown in grey) and a dedicated frequency counter
(shown in white). MG estimates the frequency of each key in the array as the
value of its counter. It returns an estimate of zero for the untracked keys.
When inserting a key~$x$, MG first checks if it has a dedicated counter in some
slot. If it does, MG increments~$x$'s counter. If not, and the array has an
empty slot, MG stores~$x$ in it with a count of~$1$. If~$x$ is not in the array
and the array is full, MG decrements all counters and discards any keys whose
counters become zero. Such keys are unlikely to be among the most frequent and
their slots are better used for tracking hotter keys. Note that~$x$ is not
stored in the newly emptied slots and is only stored if it is inserted when
some slot is already empty. MG does not support deletions. This is because it
lacks information about the untracked keys, which may become hot after the
currently hot keys are deleted, thereby failing to place them in its array.

Having more slots in the array allows MG to track more keys without discarding
them, leading to more accurate estimates. Since MG is a deterministic data
structure that does not use hashing, unlike CMS and CS, it does not suffer from
hash collisions, and its estimations have full confidence. Using an array
of~$w$ slots, MG estimates the frequency of any key with an error of at
most~$\frac{N}{w}$, i.e., $|\hat{f}(x)-f(x)| \leq \frac{N}{w}$ for any key~$x$.
Since it uses dedicated counters for the hot keys, it also provides a strong
``\emph{Tail Guarantee},'' stating that the error for any key is at
most~$\min_{1 \leq i \leq w} \frac{N^{\text{res}(i)}}{w-i+1}$, where
$N^{\text{res}(i)}$ is the total frequency of all keys not among the top~$i$.
Note that~$N^{\text{res}(i)}$ is much smaller than~$N$ when the data is skewed.

Since MG only increments a key's counter if it is in the array and decrements
counters otherwise, it only underestimates frequencies. Thus, its estimates are
biased. For similar reasons to CMS, this bias cannot be removed by enlarging
estimates. Yet, probabilistically replacing the array's least frequent keys can
yield unbiased estimates~\cite{UnbiasedSpaceSaving}. Other variations of MG
achieve higher accuracy in practice, but suffer from two-sided errors in
exchange~\cite{SpaceSaving}.

Typical implementations of MG use a hash table to implement the array of keys,
yielding constant-time queries. They also optimize insertions by lazily
decrementing the counters and employing an auxiliary heap to locate and discard
keys with zero counts.
