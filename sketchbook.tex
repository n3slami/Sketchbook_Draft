\section{Introduction}~\label{sec:introduction}
The streams we consider both insert and delete keys, which amount to
incrementing and decrementing the key's count, respectively. While some
applications such as tracking click-through rates in webpages only require
insertions, deletions are needed for other applications such as maintaining
count estimates for SQL tables for use in a query optimizer. 

Rasmus: For deletions it is critical to note that they are not ``checked for
validity'' by the sketches, so it is up to the user to ensure that deletions
correspond to insertions

We define the following two goals: \textbf{(G1)~Space-Efficient Counters}, and
\textbf{(G2)~Scaling Error with Stream Length}.

\textbf{Applications.} 
Due to its simplicity and high accuracy under skewed workloads, CMS is used in
many applications, including $k$-mer counting in
bioinformatics~\cite{CMSkmer,SetMinSketch}, network
monitoring~\cite{SketchBasedChangeDetection,WhatsNew,TrafficManagementSurvey},
and hardware security systems~\cite{CoMeT}. Yet, its biased estimates make it
less useful for applications such as join size estimation. As shown in
\Cref{sec:cs}, the Count Sketch is the tool of choice for these settings.

Since CS provides unbiased estimates, it is used in applications where
estimates are combined or multiplied to derive more complex statistics. In
particular, unbiased estimation is crucial for query
optimization~\cite{Compass,QueryOptimizationSketches,ConvolutionSketch} and
covariance estimation~\cite{ASCS}, as count estimates are multiplied in these
contexts, amplifying any bias. Other applications benefiting from CS include
feature selection~\cite{MISSION} and similarity
search~\cite{CSSetSimSearch,DensifyingLSHSketches,LasVegasSimSearch,DistanceSensitiveBloomFilters}.
CS also provides \emph{Universality}~\cite{UniversalSketching}: the ability to
estimate many statistics based on the key frequencies. This makes it a general
measurement tool for networks since it allows administrators to collect
diagnostics of any kind without needing to explicitly define the required
statistics (such as the mean, variance, and moments) beforehand~\cite{UnivMon}.

As MG accurately tracks the frequencies of heavy hitters, many other sketch
designs use it as a sub-component to reap its benefits. Moreover, because it
also stores the keys themselves, unlike CMS and CS, it is used to report the
heavy hitters, trending keys, and much
more~\cite{BatchUpdateMisraGries,AugmentedSketch,BitMatcher,BubbleSketch,HeavyGuardian,HeavyKeeper,JigsawSketch,MVSketch,SketchVisor,WavingSketch,MicroscopeSketch,PSketch,TightSketch}.

\section{Background}~\label{sec:background}
A stream is a sequence of key-value pairs~$\left\langle (x_1,\Delta_1),
(x_2,\Delta_2), \dots \right\rangle$, where~$x_i$ is the $i$-th key that
appears in the stream and~$\Delta_i = \pm1$ represents whether its count was
incremented due to an insertion ($\Delta_i=1$) or decremented due to a deletion
($\Delta_i=-1$). This is known as the \emph{General Turnstile Model} of data
streams~\cite{StreamModels}. We denote key~$x$'s count by~$f(x)$, and represent
the current total count of the keys in the stream with~$N=\sum_x f(x)=\sum_i
\Delta_i$. \Cref{tab:term_and_symbol_definitions} lists the terms and symbols
used throughout the paper.

\textbf{Exhaustive Approach.}
The simplest approach to tracking frequencies is to store each key and its
count in a hash table. Although this approach is fully accurate, it entails a
high memory overhead for three reasons: (i)~It stores all keys in the stream.
Variable-length keys worsen this overhead since they require an indirection
layer (e.g., pointers). (ii)~It stores one counter for each unique key.
(iii)~The hash table may occasionally be as much as half empty to support
collision resolution and expansions. These different overheads multiply with
the number of streams the application monitors. Problems~(i) and (ii) imply a
memory footprint that is linear in the number of unique keys in the stream,
which can be of the same magnitude as the total key count~$N$.

%(3)~Since the counters are fixed-length, each of them must be long enough to accommodate the maximum count, even if most keys have a very low count.

Frequency estimation sketches address these problems by trading accuracy for
space. That is, for any key~$x$, a sketch returns an estimate~$\hat{f}(x)$ of
$x$'s count~$f(x)$. We focus on Count-Min Sketch~\cite{CountMin} for now, as it
is the simplest and most widely used
sketch~\cite{ADSMassiveDatasetBook,SketchesTrafficManagementSurvey}. Later, we
describe Count Sketch~\cite{CountSketch} (\Cref{sec:cs}) and
Misra-Gries~\cite{MisraGries} (\Cref{sec:mg}) and apply our techniques to them.

\textbf{Count-Min Sketch (CMS).}
The core design element of CMS is a counter array consisting of~$w$ counters,
each initialized to zero. We insert a key~$x$ into this array by hashing it to
one counter and incrementing it. We delete~$x$ by decrementing its
corresponding counter.\footnote{Users must ensure deletions target previously
inserted keys. This is because frequency estimation sketches do not store the
keys and cannot check a deletion's validity.} The counter that key~$x$ hashes
to provides an estimate of~$x$'s count. Due to hash collisions, multiple keys
can map to the same counter. Because of this, we may overestimate the count of
a key~$x$. This error is at most~$\frac{N}{w}$ in expectation since a key
participates in a hash collision with a probability of~$\frac{1}{w}$ and the
total count of keys different from~$x$ is at most~$N$. Increasing the array's
size makes collisions less likely, thereby decreasing the error and improving
\emph{Accuracy}. Even so, the error may deviate from its expectation. The
probability that errors do not exceed the expectation ``too much'' is known as
the sketch's \emph{Confidence}. A straight-forward application of Markov's
inequality shows that the error does not exceed~$\frac{eN}{w}$ with a
confidence of at least~$1-e^{-1}$, i.e., $\Pr\left( |\hat{f}(x)-f(x)| \leq
\frac{eN}{w} \right) \geq 1-e^{-1}$ for any key~$x$. Here, we use Euler's
constant~$e$ due to convention. Any other constant would also work and would
replace~$e$ in both the accuracy bound and the confidence. This implies that
the smaller the constant becomes, i.e., the more accurate we expect the sketch
to be, the lower confidence drops.

Yet, with a single array, confidence is low ($\approx 63\%$). The reason is
that all keys sharing the same counter as a frequent key will suffer from
inflated estimates. Moreover, since there are many keys with low or moderate
counts, there is a non-negligible chance that enough of them map to the same
counter and inflate estimates beyond the error bound. CMS addresses these
issues by allocating~$d$ independent counter arrays, each with a dedicated hash
function~$h_i$. CMS inserts or deletes a key by applying the operation to each
array, and it answers a query by querying all arrays and taking the minimum of
the estimates.\footnote{CMS uses pairwise-independent hash functions to bound
the probability of collisions and overestimation~\cite{CountMin}.}
\Cref{fig:cms_overview} shows an example of insertions and queries applied to
three counter arrays. Returning the minimum for queries boosts confidence
exponentially, since it only carries severe errors when all estimates err
significantly. Thus, CMS guarantees an error of at most~$\frac{eN}{w}$ with a
confidence of~$1-e^{-d}$, i.e., $\Pr\left( |\hat{f}(x)-f(x)| \leq \frac{eN}{w}
\right) \geq 1-e^{-d}$ for any key~$x$.

Since CMS uses a constant number of tightly packed counters and does not store
the stream's keys, it significantly improves the memory footprint compared to
the exhaustive approach of tracking each key's exact count. Nevertheless, CMS
still suffers from several memory inefficiencies, as we show in the following
section.

\section{Problem Analysis}\label{sec:problem_analysis}
Traditional frequency estimation sketches, such as CMS, use more memory than
necessary by failing to account for 1)~the skew in the stream and 2)~the
stream's gradual growth over time.

\textbf{Challenge 1: Skew.}
With uniform workloads, most counters in CMS take on similar values. In
contrast, under skewed workloads with a few heavy hitters, most counter values
remain small while only a few grow large. Because CMS relies on uniformly sized
counters that must be sufficiently long to store the maximum counter value, it
wastes substantial memory by allocating excessive bits to the many counters
with small values. Ideally, each counter should be just long enough to fit its
value, thereby saving space or allowing more counters to improve accuracy.

A common strategy for tackling this problem is to track the heavy hitters
separately in a hash table while leaving the rest of the keys to
CMS~\cite{AugmentedSketch,HeavyKeeper,HeavyGuardian,MVSketch,WavingSketch,ElasticSketch}.
Such hybrid structures aim to cap the maximum counter value in CMS, thereby
permitting shorter counters. Yet, this approach does not fundamentally resolve
the issue. The keys tracked by CMS may still follow a skewed distribution,
leading to significant memory wastage. Moreover, the heavy hitters can vary
over time. Identifying the next heavy hitter and ``promoting'' it from CMS into
the hash table is error-prone, since collisions in CMS can cause many
infrequent keys to be misclassified as heavy hitters. The hybrid structures in
the literature explore different hash table implementations and promotion
policies.

Other approaches compress the counters using algorithms such as compressive
sensing~\cite{TreeSensing,BitSense} or hypergraph peeling~\cite{CodingSketch}.
Yet, these methods impose heavy decompression overheads on queries.

Counter sharing approaches store the counter values in a hierarchy of counters,
with the lowest level storing the counter values in short counters and the
upper levels handling overflows using shared
counters~\cite{BitSense,PyramidSketch,StingySketch,AdaptiveCounterSplicing,CounterTree,TreeSensing}.
The left side of \Cref{fig:counter_sharing_merging} encodes four adjacent
counters within CMS using such a hierarchy with 6{\nobreakdash-}bit and
2{\nobreakdash-}bit counters. Whenever a counter in this hierarchy overflows,
it increments its parent and resets itself back to zero. A counter's value is
retrieved by concatenating the counters along its path to the root until
reaching a delimiter, typically indicated using additional metadata. While
counter sharing yields state-of-the-art accuracy and performance for short
streams, its error rapidly deteriorates as the stream grows. In particular,
after~$N$ insertions into an array of size~$w$, each counter overflows into
the~$\Theta(\log (N/w))$ levels above it. This blows up the values
of~$\Theta(N/w)$ other counters, increasing the estimation error by the same
factor. The counter sharing methods in the literature experiment with the
hierarchy’s structure, including aspects like the counter sizes and the fanout.

Counter merging is an alternative approach that starts with 8-bit counters and
merges adjacent overflowing counters into a longer counter that sums up the
original values~\cite{SALSA}. The right side of
\Cref{fig:counter_sharing_merging} applies this scheme to CMS. After~$N$
insertions into an array of~$w$ counters, each counter will be merged
with~$\Theta(\log (N/w))$ other counters, increasing the error by the same
factor. Merging only continues until the counters become the same length as
those of CMS, at which point error degradation stops. Counter merging has a
higher metadata overhead than counter sharing for indicating which counters are
merged, leaving less space for storing counters. Parsing this metadata is also
complex, reducing performance.

Deletions deteriorate the accuracy of both counter sharing and counter merging
methods since these techniques ambiguate how counters should be ``separated''
as they decrease. 

\Cref{fig:counter_sharing_deterioration} qualitatively compares counter sharing
and counter merging to CMS to illustrate their error degradation with data
growth, under the same memory budget. While these methods perform well for
short streams, their error exceeds that of CMS as the stream grows. We
empirically verify this behavior in \Cref{sec:evaluation}.

\textbf{Challenge 2: Unbounded Growth.}
In many streaming applications, the data stream grows continuously, and it is
imperative to estimate the count of each key from the stream's beginning. For
instance, query optimizers often track the number of times each key occurs in a
table column to estimate the size of a join on that
column~\cite{Compass,QueryOptimizationSketches,ConvolutionSketch}. As new data
is inserted, the total number of keys~$N$ increases. Yet, the full count
history of each key is still needed, since every occurrence contributes equally
to the join size regardless of when it arrived.

Unbounded stream growth is also a challenge for applications that only require
key counts over recent time windows. For example, network management systems
detect anomalous or malicious activity by counting packets from each source
within fixed time
windows~\cite{SketchBasedChangeDetection,WhatsNew,TrafficManagementSurvey}.
With bursty streams such as network traffic, the number of keys~$N$ in each
window is unpredictable.

In existing frequency estimation sketches, the number of counters~$w$ is fixed
at allocation time. Consequently, the error rate degrades linearly with~$N$
(e.g., $N/w$ in the case of CMS). This forces practitioners to tune~$w$ without
knowledge of the final stream length, hoping to balance accuracy and the memory
footprint. Having too few counters leads to significant errors, while having
too many wastes memory. Deletions make the problem more challenging by
causing~$N$ to fluctuate over time. Worse yet, even if the ultimate stream
length is known upfront, allocating a large CMS from the start wastes memory
during the early stages when the stream is short.

\textbf{Summary.}
An ideal frequency estimation sketch should: 1)~compactly encode counter values
without incurring memory waste from skew, 2)~scale its size with the stream's
length to keep both the memory footprint and the error rate under control,
3)~support deletions without sacrificing accuracy, and 4)~provide
high-performance operations. Is it possible to achieve all these goals
simultaneously?

\section{\sketch}\label{sec:sketchbook} 
We present \sketch, a framework for generalizing a frequency estimation sketch
to optimize its memory footprint with respect to the stream's skew and its
length. \Cref{sec:accommodating_skew} shows how to adapt to skew by compactly
encoding each counter as a short integer and extending it as it overflows.
\Cref{sec:accommodating_unknown_stream_lengths} shows how to control both
accuracy and space for a stream of unknown length by expanding and contracting
the sketch. At the same time, \sketch\ supports deletions and maintains high
performance. We first describe \sketch\ as applied to the Count-Min
Sketch~(CMS), denoted as \sketchcms. We apply it to other sketches in
\Cref{sec:cs} and \Cref{sec:mg}.

\subsection{Accommodating Skew}\label{sec:accommodating_skew}
Under skew, many counter values in CMS will be small and not use all the bits
in their counters. To optimize the space used for storing these counter values
in any workload, \sketchcms generalizes CMS with a general-purpose
\counterencoding~(\counterencodingabbrv) encoding. \counterencodingabbrv\
stores the counters as fixed-size integers called \emph{Stubs}. When a counter
overflows its stub, \counterencodingabbrv\ elongates it with a dedicated
variable-length \emph{Extension}. Due to their need for delimiters, storing
extensions entails a slight metadata overhead. We counteract this overhead by
choosing the stub length based on the workload’s skew so that more counter
values fit in their stubs without needing extensions. More precisely, we choose
the shortest stub length that minimizes the total memory footprint of the stubs
and the extensions. We adapt this stub length to the workload by reconfiguring
it when the total number of overflows exceeds a threshold. To improve cache
behavior and quickly reconstruct a counter, \counterencodingabbrv\ colocates a
stub and its corresponding extension in the same cache line. It quickly finds a
stub's extension using a bit manipulation workflow that leverages rank and
select operations.

\textbf{Chunking.}
To colocate stubs and their extensions in 512-bit cache lines,
\counterencodingabbrv\ partitions each counter array into contiguous
\emph{Chunks}, each occupying a cache line. A chunk stores its counters' stubs
in a contiguous array and tracks the counters that overflow their stubs using
an \emph{Overflows Bitmap} with one bit per counter. It stores the extensions
of these overflowing counters contiguously in the remaining space towards its
end, called its \emph{Extension Pool}. Counter~0 and Counter~1 in
\Cref{fig:counter_chunk} are examples of a non-overflowing and overflowing
counter within a chunk, respectively.

\textbf{Parameters.}
\counterencodingabbrv\ has two parameters: the number of bits in each stub~$s$
and the number of counters per chunk~$c$. With more skewed workloads, having
shorter stubs and more counters per chunk reduces space consumption. The reason
is that skew shrinks most counter values, enabling the use of shorter stubs for
storing them. Skew also reduces the average length of the extensions, leaving
more space in a chunk to store more counters.

Later in this section, we discuss how to adapt the tuning of these parameters
to the workload as the stream evolves. When the workload is uniform, this
procedure tunes the stub length so that all counter values fit in stubs,
allowing it to remove the overflows bitmaps and yield the configuration of a
standard CMS. We illustrate the impact of this procedure on the memory
footprint in \Cref{sec:evaluation}.

\textbf{Extensions.}
We form extensions from 2{\nobreakdash-}bit \emph{Fragments} to encode the
higher-order bits of overflowing counters succinctly and to extend them at the
finest possible granularity. We use the fragment~$11$ as a delimiter at the end
of each extension. The other three combinations of bits are used to encode each
extension's value in base 3. Specifically, the base{\nobreakdash-}3
digits~$(0)_3$, $(1)_3$, and $(2)_3$ are represented as the
fragments~\textit{00}, \textit{10}, and \textit{01}, respectively. We store
fragments in increasing order of their digits' significance from left to right.
Formally, a value~$v$ is encoded in an extension by representing each of
its~$\left\lfloor \log_3 v \right\rfloor + \nolinebreak 1$ digits in a
fragment, with the~$j${\nobreakdash-}th digit being~$v_j=\left\lfloor v/3^j
\right\rfloor \mod 3$. We decode~$v$ back into decimal by computing the
sum~$3^0 \cdot v_0 + 3^1 \cdot v_1 + \dots$.

For example, the value~5, which is the value of the higher-order bits of
Counter~1 in \Cref{fig:counter_chunk}, has two digits in base 3. It is
therefore encoded as the extension~$\langle (2)_3, (1)_3, \text{delimiter}
\rangle=\langle \text{\textit{01}}, \text{\textit{10}}, 11 \rangle$. Decoding
this extension yields~$3^0 \cdot 2 + 3^1 \cdot 1 = 5$, as expected.

Forming a chunk's extensions from 2-bit fragments allows them to fit in 1-2
machine words in most cases. We prove in \Cref{sec:theoretical_analysis} that
using these extensions in conjunction with short stubs enables
\counterencodingabbrv\ to encode each counter's value in space close to the
length of its binary encoding. 

Treating arbitrary variable-length data as counters allows
\counterencodingabbrv\ to compactly encode them. Thus, it can be used in other
applications operating on such data to improve memory efficiency.

\textbf{Locating an Extension.}
To decode an overflowing counter, \counterencodingabbrv\ must locate its
extension. To this end, it keeps the extensions in the same order as that of
the counters. It locates the~$i${\nobreakdash-}th counter's extension by
counting the number of preceding bits set to~1s in the overflows bitmap. This
is equivalent to the number of overflowing counters preceding
the~$i${\nobreakdash-}th counter, denoted by~$m$. Skipping over the first~$m$
extensions in the extension pool leads to the position of the target extension.

\Cref{fig:extension_location_example} illustrates the process of identifying
the 3rd counter's extension in a chunk. Here, since the 3rd bit in the
overflows bitmap is~1, the 3rd counter has an extension. As there is one bit
set to~1 preceding the 3rd bit in the overflows bitmap, we skip one extension
to locate the 3rd counter's extension, shown in gray.

\textbf{Fast Access Using Rank and Select.}
\counterencodingabbrv\ quickly locates the extension of an overflowing counter
using rank and select
operations~\cite{Poppy,FlorianRankandSelect,CompactPATTrees,RankandSelectDict,GQF}.
Given a bitmap~$B$, the $\texttt{rank}(i,B)$ operation counts the number of~1s
strictly before the $i$-th bit, and the $\text{select}(i,B)$ operation returns
the position of the~$i${\nobreakdash-}th 1. Later in this section, we show how
to use specialized CPU instructions to implement these operations efficiently. 

The first step is to determine~$m$, the number of overflowing counters to the
left of the~$i${\nobreakdash-}th counter. As this is the number of 1s before
the $i${\nobreakdash-}th bit in the overflows bitmap, \counterencodingabbrv\
applies the rank operation to evaluate~$m=\texttt{rank}(i,$~overflows$)$.

The second step is to identify the target extension's delimiter by skipping
over the~$m$ delimiters preceding it. We do this using several bit manipulation
techniques. First, we convert the extension pool into a so-called
\emph{Delimiters Bitmap}. This bitmap contains one bit set to~1 at the position
of every delimiter and~0s everywhere else, as illustrated at the bottom right
of \Cref{fig:extension_location_example}. To derive this bitmap, we take the
bitwise-and of the extension pool with a version of itself shifted to the right
by one bit. The result is a bitmap with a~1 at the end of any two
consecutive~1s in the original extension pool, as illustrated in
\Cref{fig:extension_location_example}. This means that every bit in this bitmap
corresponding to the second bit of a fragment is set to 1 if the fragment is a
delimiter and is set to 0 otherwise. We mask out all other bits to 0s. In sum,
the delimiters bitmap is derived as
\begin{center}
    delimiters $=$ extensions \& $($extensions >‌> 1$)$ \& $0101\dots0101$.
\end{center}
Finally, we use the select operation to
evaluate~$\texttt{select}(m,$~delimiters$)$, which skips over the first~$m$
delimiters and returns the position of the~$m${\nobreakdash-}th delimiter. We
sequentially apply the bitwise operations above to each machine word comprising
the chunk's extensions. This is efficient, as a chunk's extensions often fit in
1-2 words.

\Cref{fig:extension_location_example} shows an example of locating the 3rd
counter's extension using rank and select. Here,
$\texttt{rank}(3,$~overflows$)=1$. Thus, after deriving the delimiters bitmap
by manipulating the extension pool, \counterencodingabbrv\
evaluates~$\texttt{select}(1,$~delimiters$)=9$ to conclude that the target
extension ends at the~9th bit.

\textbf{Tails.}
In the rare event that many heavy hitters hash to the same chunk, many of the
chunk's counters will overflow, potentially growing the cumulative length of
the extensions beyond the size of the chunk. \counterencodingabbrv\ handles
this case by allocating an external array of 32-bit integers called
\emph{Tails} for the chunk, with one tail integer per counter. It stores
the~$i${\nobreakdash-}th counter's higher-order bits in
the~$i${\nobreakdash-}th tail. Each chunk contains a mode flag indicating if it
has a tails array, as depicted in \Cref{fig:counter_chunk_with_tails}. If it
does, we repurpose the space taken up by the extension pool to store a pointer
to the tails array. We ensure that the extension pool is large enough to
accommodate this pointer (i.e., at least 48 bits\footnote{The upper 16 bits a
general 64-bit pointer are unused on modern machines. As such, we only store
the lower 48 bits of the pointer.}) when tuning the number of counters per
chunk and the stub size. Any space after the pointer is unused.

\textbf{Adaptive Tuning.}
If more than~$1\%$ of the chunks use tails arrays after an insertion or if
there are more than two unused bits per counter after a deletion, \sketchcms
adapts \counterencodingabbrv's tuning, i.e., the number of counters per
chunk~$c$ and the stub length~$s$, to minimize the memory footprint. It does
this by scanning the entire sketch and computing the number of counter values
of every binary length. It uses this summary to calculate the expected total
length of a chunk's extensions for a given combination of parameters~$c$ and
$s$. It enumerates the possible combinations by first varying~$c$ from largest
to smallest and enumerating the stub length~$s$ from smallest to largest for
each fixed~$c$. For each combination, it then applies Chebyshev's inequality to
the total extension length to derive a conservative bound on the number of
chunks that will use tails arrays. It chooses the first combination that yields
a bound smaller than~$0.5\%$. In doing so, \sketchcms ensures
\counterencodingabbrv\ packs as many counters as possible within each chunk and
the stubs have as few unused bits as possible. It also ensures that extensions
rarely outgrow their chunks, making the memory overhead of the tails arrays
negligible. The amortized overhead of this tuning process is constant, as many
more insertions and deletions compared to the number counters must take place
before this process is triggered.

\textbf{Incrementing Counters.}
When an insertion maps to the~$i${\nobreakdash-}th counter of a chunk,
\sketchcms increments it by adding one to the lower-order bits stored in
the~$i${\nobreakdash-}th stub, i.e., stub[$i$]. Most of the time, stub[$i$]'s
increment will not carry over to the higher-order bits of the counter, allowing
the insertion to return early and achieve high throughput. 

Whenever stub[$i$]'s increment carries over, \sketchcms adds one to the
counter's extension or tail. For an extension, this entails incrementing its
first digit and propagating a carry to the other digits as necessary. This
carry may propagate beyond the end of the extension, leading to the addition of
a new digit. \sketchcms makes room for the fragment representing this digit by
shifting subsequent extensions to the right. If the~$i${\nobreakdash-}th
counter did not have an extension, a new extension encoding the value~1 is
created for it. We use rank and select operations to determine the appropriate
position of this extension in the extension pool.

\textbf{Decrementing Counters.}
Analogously, when a deletion maps to the~$i${\nobreakdash-}th counter in a
chunk, \sketchcms decrements the lower-order bits in~stub[$i$]. If stub[$i$]
borrows from the counter's higher-order bits as a result, \sketchcms decrements
the corresponding extension or tail. This may trigger the removal of a digit
from the counter's extension, in which case subsequent extensions are shifted
to the left to keep the extension pool tightly packed. 

\textbf{Optimization~1: Fast Division.}
Determining the chunk of a counter at offset~$i$ in an array is expensive, as
it entails dividing~$i$ by the number of counters per chunk~$c$, which may not
be a power of two. We avoid this cost by simulating the division through
fixed-point multiplication. Specifically, we compute the
expression~$\left\lfloor \left(i/2^{\lceil \log_2 c \rceil}\right) \cdot
\left(2^{\lceil \log_2 c \rceil}/c\right) \right\rfloor = \left\lfloor i/c
\right\rfloor$ by representing the multiplicands as fixed-point fractional
numbers. To this end, we precompute the latter multiplicand's fixed-point
representation with~$\left\lceil \log_2 w \right\rceil$ bits of precision,
where~$w$ is the size of an array. For the former multiplicand, we treat~$i$'s
binary representation as a fixed-point fractional value with the decimal point
being after the~$\left\lceil \log_2 c \right\rceil${\nobreakdash-}th bit.
Finally, we multiply these values using standard integer multiplication and
shift the result~$\left\lceil \log_2 w \right\rceil + \left\lceil \log_2 c
\right\rceil$ bits to the right to remove the fractional bits and compute the
answer.

\textbf{Optimization~2: Hardware Accelerated Rank and Select.}
\sketchcms utilizes specialized CPU instructions to implement rank and select
operations. It implements~$\texttt{rank}(i,B)$ by applying the \verb|POPCNT|
instruction to the first~$\left\lceil i/64 \right\rceil$ words of the
bitmap~$B$ to count the~1s before the~$i${\nobreakdash-}th
bit.\footnote{Formally, denoting the~$j${\nobreakdash-}th word in~$B$ as~$B_j$,
this process corresponds to computing \texttt{POPCNT}$ \left(B_{\lfloor i/64
\rfloor}\text{~\&~}((1 \text{ <‌< } (i \mod 64))-1) \right) +
\sum_{j=0}^{\lfloor i/64 \rfloor -1}$ \texttt{POPCNT}$(B_j)$.} It also
implements~$\texttt{select}(i,B)$ by counting the 1s
in~$B$'s words to locate the word containing the $i${\nobreakdash-}th~1. Once
found, it applies the x86 instructions \verb|PDEP| and \verb|TZCNT| to evaluate
the target bit's position within that word, as described in
\cite{GQF}.\footnote{If the~$j${\nobreakdash-}th word $B_j$ contains
the~$i${\nobreakdash-}th 1 and there are~$r$ 1s in the preceding words, the
result is computed as~$64 \cdot j + $\texttt{TZCNT}$($\texttt{PDEP}$((1 \text{
<‌< } (i-r)) - 1, B_j))$, where the first operand of \texttt{PDEP} is the
payload and the second operand is the mask~\cite{PDEP}.} Each of these commands
is applied to 1-2 machine words, as the bitmaps \sketchcms operates over are
1-2 words long.

\textbf{Optimization~3: Lookup Tables.}
Since stubs are not byte-aligned, modifying them can be costly. This is because
extracting and writing back a stub to the machine words containing it entails
five extra bitwise operations on top of the addition operation. \sketchcms
bypasses this cost by directly updating the stub's words using a single
addition. It achieves this using two precomputed lookup tables. The first table
stores the position of the word each stub lies in, and the second table stores
the stub's position within its word. \sketchcms updates a stub by adding or
subtracting one from the bit indicated by the second table in the word
indicated by the first. For example, in the context of
\Cref{fig:counter_chunk}, the first lookup table indicates that the~1st stub
lies in the 1st word, which has a binary representation of~$111111101010\dots$.
The second lookup table indicates that this stub starts at the~6th bit in the
1st word, allowing us to increment it by adding~$000000100000\dots$, thus
yielding~$111111011010\dots$ as the updated word.

\textbf{Optimization~4: Prefetching.}
We allow multiple chunks to be read in parallel within a single operation as
well as across multiple operations using prefetching techniques similar to that
of~\cite{StingySketch}. Specifically, we maintain a prefetching queue for each
array in \sketchcms that records the eight most recent requests for chunks.
Each time a chunk is requested from an array, a software prefetch instruction
is issued for it, and the request is pushed into the array's queue. When a
queue fills up, the chunk of its oldest request will be present in the L1
cache, allowing it to be read efficiently while other chunks are being loaded
into the cache. 

\textbf{Optimization~5: Hash Splicing.}
Recall that a key is hashed into each of the sketch's~$d$ arrays during an
update or query. Instead of applying~$d$ separate hash functions and incurring
their CPU overheads, \sketchcms applies a single hash function to the key to
compute a long hash. It splices the result into~$d$ sub-hashes of equal length
and uses each as the hash value of an array.

\subsection{Accommodating Unbounded Growth}\label{sec:accommodating_unknown_stream_lengths}
Recall from \Cref{sec:problem_analysis} that processing growing streams with
existing frequency estimation sketches (e.g., CMS) yields an estimation error
that deteriorates linearly with the total key count~$N$. \sketch\ addresses
this issue for each sketch by generalizing it to expand the number of its
counters as the stream grows. In the case of CMS, \sketchcms first allocates a
sketch with arrays consisting of a few counters. It inserts and deletes keys
from this sketch until~$N$ exceeds an internally chosen threshold. Once this
occurs, \sketchcms expands by allocating a new sketch with arrays twice the
size of those in the old sketch, with counters initialized to zeros. It directs
insertions and deletions to this new sketch so that they benefit from its
higher tracking accuracy. Whenever~$N$ again exceeds a threshold, \sketchcms
allocates another sketch double the size of the previous one. It arranges these
sketches from oldest to newest in a chain, yielding the structure shown in
\Cref{fig:sketchbook_chain}. All sketches along this chain have the same number
of arrays~$d$ to enable a constant confidence bound. A query checks each sketch
in the chain, sums the estimates from corresponding arrays, and reports the
minimum.

Unlike arrays or hash tables, which expand when~$N$ doubles, \sketchcms expands
after~$N$ more than doubles to achieve both sub-linear errors and a sub-linear
memory footprint. More precisely, it chooses the expansion thresholds as the
values of~$N$ that double the value of a user-defined \emph{Size Function},
denoted as~$W(N)$. We set~$W(N)=\sqrt{N}$ by default, which corresponds to
expanding the sketch whenever~$N$ quadruples, as shown at the bottom of
\Cref{fig:sketchbook_chain}. These thresholds keep the size of the last
sketch's arrays within a factor of two of~$W(N)=\sqrt{N}$. Moreover, they cause
the last sketch to process the majority of the stream, making it the dominant
factor in both the overall error bound and memory. Intuitively, this means that
\sketchcms simulates processing the entire stream with a sketch allocated
upfront with arrays of size~$\sqrt{N}$, as if~$N$ was known.

\textbf{Contractions.} 
When deletions decrease~$N$ below the previous expansion threshold, i.e.,
whenever~$N$ drops by $4\times$, \sketchcms contracts to save memory. It does
so by transferring the updates of the last sketch to the penultimate sketch and
discarding the last sketch. This transfer is challenging, as we do not have
access to the keys and thus cannot rehash them into the penultimate sketch. We
overcome this issue by using~$d$ shared hash functions~$h_1,\dots,h_d$ for the
sketches, each computing a long \emph{Mother
Hash}~\cite{PaghExpandability,InfiniFilter,AlephFilter} for a given key. To map
a key~$x$ to a counter in the~$i${\nobreakdash-}th array of a sketch, we
compute~$h_i(x)$ to derive its mother hash. Letting~$w$ denote the size of this
array, we take the~$\log_2 w$ lower-order bits of~$x$'s mother hash as the
offset of the counter it hashes to. \Cref{fig:contraction} shows this procedure
for the first arrays of the chain's last two sketches.

This hashing scheme allows \sketchcms to determine the counter a key hashes to
in the penultimate sketch by removing the most significant bit (MSB) of its
counter's offset in the last sketch. Thus, adding the value of the latter
counter to the former transfers the effects of all updates that hashed to it.
Since the MSB value of the counters' offsets partitions the last sketch into
two halves, transferring all updates amounts to adding each partition to the
penultimate sketch. We illustrate this at the bottom of \Cref{fig:contraction}.

Because the majority of the stream's keys must be deleted to trigger a
contraction, the last two sketches of the chain always handle the majority of
the stream's keys. Therefore, together, they are the dominant factor in both
the overall error bound and memory. As such, the error remains bounded, despite
the state of each sketch in the chain depending on the sequence of insertions
and deletions.

As shown in \Cref{fig:contraction}, deletions may turn the counters in the last
sketch negative. We shortly show how to avoid such negative counters by
aggregating the old sketches into the last one.

\textbf{Aggregating Sketches.}
While insertions and deletions only affect the last sketch in the chain,
queries must probe all sketches and aggregate their results. \sketchcms speeds
up this process by aggregating the updates of all older sketches into the last
one without incurring extra errors. It achieves this by leveraging the mother
hashes. As before, removing the MSBs of the offset of a key~$x$'s counter in
the last sketch yields the offset of the counter it hashes to in an older
sketch, as shown in \Cref{fig:aggregating_sketches}. By aggregating the value
of the latter counter into the former, we ensure that querying~$x$ in the last
sketch takes into account the old counter's value without needing to probe the
old sketch directly. Applying this procedure to all counters in the last sketch
amounts to partitioning the last sketch based on the MSBs of its counters'
offsets and adding the old sketch to each partition. 

Counters in the aggregated sketch cannot be negative. This is because a
negative aggregated counter corresponds to the user deleting a key more times
than inserting it, which is impossible.

\textbf{Insert-Only Workloads.}
Contractions never occur in insert-only streams. Here, the old sketches are
redundant, as they only serve to reconstruct the last sketch from the
aggregated sketch during contractions. In such cases, \sketchcms discards the
old sketches to reduce the memory footprint by at least 50\%.

\textbf{Size Function.} 
Setting the size function~$W(N)$ to functions other than~$\sqrt{N}$ exposes a
rich spectrum of accuracy-memory tradeoffs. The faster the size function grows
with respect to the total key count~$N$, the sooner \sketchcms expands, thereby
tracking more of the stream's keys more accurately in exchange for a larger
memory footprint. We recommend setting the size function to a \emph{Sub-Linear
Power} of the form~$W(N)=N^\alpha/\epsilon$ and tuning the constants~$\alpha
\in [0,1)$ and $\epsilon$. Using such functions captures the behavior of
expanding when~$N$ increases by a constant factor larger than two. We prove in
\Cref{sec:theoretical_analysis} that using a sub-linear power yields an error
bound of~$O(N/W(N))=O(\epsilon \cdot N^{1-\alpha})$. This matches the error
bound of a sketch preallocated with arrays of size~$W(N)$, which is
optimal~\cite{CountMin}. Setting~$\alpha=0.5$ and $\epsilon=1$ yields the
default~$W(N)=\sqrt{N}$.

One may hope to achieve~$O(\epsilon)$ errors by setting~$W(N)=N/\epsilon$. This
translates to \sketchcms expanding when~$N$ doubles. Yet, we prove in
\Cref{sec:theoretical_analysis} that, without knowing the ultimate length of
the stream, the best error bound achievable by a sketch that
maintains~$O(N/\epsilon)$ counters\footnote{More precisely, we show this for
any sketch using~$O\left( N/\epsilon \cdot \frac{\log\log N}{\log N} \right)$
bits of space.} is~$O(\epsilon \cdot \log N)$. By setting~$W(N)=N/\epsilon$ and
applying slight space optimizations, \sketchcms attains this error bound under
the same memory budget and is thus optimal.

\subsection{Applying \sketch\ to Count Sketch}\label{sec:cs}
%For example, in join size estimation, multiplying overestimated counts from the input tables leads to an overly large join size.

\textbf{Count Sketch (CS).}
CMS, as described in \Cref{sec:background}, has two key shortcomings: (1)~its
estimations are biased since it only overestimates and (2)~its errors compound
when it is used in some tasks, particularly those that multiply frequencies. CS
addresses these issues by providing unbiased estimates.\footnote{In CMS, one
can subtract the average of the counter values a query key does not hash to
from the query's counter to derive an unbiased estimate~\cite{CountMeanMin}.
Yet, the resulting estimate has a marginally higher variance than that of CS.}
The first two rows of \Cref{tab:classic_sketch_stats} summarizes the properties
of CS and compares it to CMS.

The core component of CS is a counter array of size~$w$ coupled with a hash
function~$h_i$ mapping a key to a counter. CS further associates with each key
a random ``update direction'' from the set~$\{-1,+1\}$ by hashing it with
another hash function~$\sigma_i$.\footnote{The~$\sigma_i$ form a 4-wise
independent family of hash functions, yielding a bound on the probability of
large errors~\cite{CountSketch}.} It inserts a new key~$x$ by incrementing or
decrementing its counter according to~$\sigma_i$, as shown in
\Cref{fig:cs_overview}. CS deletes~$x$ by subtracting~$\sigma_i(x)$ from its
counter to undo its insertion. Since each key's update direction is random, the
expected interference on~$x$'s counter from any other key is zero due to the
positive and negative possibilities canceling out. Thus, the value of the
counter along the update direction is an estimate of~$x$'s frequency, which CS
returns during a query. Although this estimate may be smaller or larger than
the ground-truth frequency, the zero expected interference allows it to match
the ground-truth on average, removing bias. Increasing the array's size reduces
the likelihood of hash collisions and the average deviation.

As with CMS, a frequent key will adversely impact the estimates of keys sharing
the same counter, degrading confidence. CS addresses this by employing~$d$
independent arrays, each with its own hash functions~$h_i$ and $\sigma_i$.
Unlike CMS, CS cannot answer a query by returning the minimum estimate, as it
may greatly underestimate the result due to two-sided errors. Instead, it
returns the median estimate, as shown in \Cref{fig:cs_overview}. This improves
confidence since severe errors are unlikely to occur for enough experiments to
affect the median. CS takes the median instead of the mean to improve
robustness to outlier estimates. With~$d$ arrays with~$w$ counters each, CS
guarantees an error bound of at most~$\sqrt{\frac{e \cdot \sum_{y}
(f(y))^2}{w}}$ with a confidence of~$1-e^{-d}$, i.e., $\Pr\left(
|\hat{f}(x)-f(x)| \leq \sqrt{\frac{e \cdot \sum_{y} (f(y))^2}{w}} \right) \geq
1-e^{-d}$ for any key~$x$. The error term above is smaller than CMS's error
term when the frequency distribution is less skewed, as the root slows its
growth to~$O(\sqrt{N})$ (vs.~$N$) when the summands are small. The
quantity~$\sqrt{\sum_y (f(y))^2}$ is known as the~$\ell_2$-norm of the key
counts in the stream, which we denote by~$N_2$.

\textbf{Accommodating Skew.}
Similarly to CMS, CS wastes memory under skewed workloads due to using
uniformly-sized counters. \sketchcs addresses this problem by generalizing CS
to use a tailored version of \counterencodingabbrv. To this end, it appends a
sign bit to each stub. This allows it to store negative counter values by
setting the corresponding sign bit to~1 and using \counterencodingabbrv\ as
before to encode the counter's absolute value.

\textbf{Accommodating Unbounded Growth.}
As with CMS, using CS to process a growing stream yields estimation errors that
grow with the total key count~$N$. To resolve this problem, \sketchcs extends
CS to expand the number of its counters. To this end, it creates a chain of
sketches, similar to that of \sketchcms. It applies the same hashing scheme
with the use of mother hashes, but also makes use of
shared~$\sigma_1,\dots,\sigma_d$ to derive consistent update directions across
the sketches. It applies the same expansion and contraction procedures, and
handles a query by summing the estimates of the corresponding arrays and taking
the median. It also speeds up queries by aggregating the old sketches into the
last one.

\sketchcs differs from \sketchcms in one key aspect: the estimation error of a
sketch in its chain with arrays of size~$w$ scales with the
stream's~$\ell_2$-norm, i.e., as $\sqrt{N_2^2/w}$, as opposed to~$N/w$. The
value of~$N_2$ varies based on the workload, with uniform workloads having~$N_2
\approx \sqrt{N}$ and skewed workloads having~$N_2 \approx N$. \sketchcs must
therefore expand based on~$N_2^2$ to minimize its memory footprint while
ensuring bounded errors for any workload. To this end, it defines its size
function as~$W(N_2^2)$. Whenever~$W(N_2^2)$ doubles, it expands, and whenever
it halves, it contracts. 

To compute~$W(N_2^2)$, \sketchcs must track~$N_2$. It does so by employing an
array of AMS sketches to approximate~$N_2$~\cite{AMS}. An AMS sketch is a
specialized CS with a single array consisting of a single counter. Each
insertion increments the counter along its update direction and a deletion
decrements it. The following theorem holds for AMS sketches:
\begin{theorem}[Theorem 2.2 of~\cite{AMS}, specialized]
    One can approximate~$N_2^2$ within a factor of two with a probability
    of~$1-p$ using~$4 \cdot \log 1/p$ AMS sketches. Estimation proceeds by
    squaring the sketches, averaging them in groups of~4, and taking the
    median.
\end{theorem}
Thus, it suffices to keep~$O(\log N)$ AMS sketches in memory to
approximate~$N_2$ with high probability at all points in time. Since~$N$ is
bounded by the maximum value representable in a 64-bit machine word in
practice, \sketchcs employs~64 AMS sketches. It uses SIMD to quickly
update\footnote{More generally, it is possible to maintain~$k$ AMS sketches,
where~$k$ is the machine word size, in constant time with high probability to
approximate~$N_2$. We omit the proof of this statement due to space
constraints.} and query these sketches.

Similarly to \sketchcms, using a sub-linear power size function of the

\textbf{Memory Footprint.}
Since \counterencodingabbrv's tuning procedure ensures few bits are unused per
counter and few chunks use tails arrays, {\sketch}'s memory footprint is
dominated by the space occupied by the stubs and the extensions. For a single
counter, this cost is:
\begin{lemma}
    \label{lemma:single_counter_space}
    When working with unsigned counters and stubs of length~$s$,
    \counterencodingabbrv\ encodes a counter value~$v$ in $s$ bits if $v < 2^s$
    and in $4 + 1.26 \cdot \log_2 v$ bits otherwise. Signed counters take one
    more bit to encode the sign in both cases.
\end{lemma}
\begin{proof}
    If~$v < 2^s$, it fits in its stub and occupies~$s$ bits. Otherwise, its~$s$
    lower-order bits are stored in its stub, and its higher-order bits
    encoding~$\lfloor v/2^s \rfloor$ are stored in an extension. This extension
    has~$\lfloor \log_3 \lfloor v/2^s \rfloor \rfloor + 2$ fragments to
    represent the digits and the delimiter. Thus, it occupies
    $$ 2 \cdot (\lfloor \log_3 \lfloor v/2^s \rfloor \rfloor + 2) \leq 2 \cdot (\log_3 2 \cdot \log_2 \lfloor v/2^s \rfloor + 2) \leq 4 - s + 1.26 \cdot \log_2 v $$
    bits. This, combined with the cost of the stub, yields the result.
\end{proof}
Applying \Cref{lemma:single_counter_space} to all counters yields:
\begin{theorem}
    \label{thm:all_counters_space}
    When an array of~$w$ counters has processed at total of~$N$ increments and
    decrements, its total memory footprint is~$O(w \cdot (\log_2 (N/w) + 1))$
    bits. Applied to all~$d$ arrays in \sketch\ when sketches are not
    aggregated, this corresponds to a memory footprint of~$O(d \cdot W(N) \cdot
    (\log_2 (N/W(N)) + 1))$ bits.
\end{theorem}
\begin{proof}
    Denoting the signed value of the~$i${\nobreakdash-}th counter by~$v_i$ and
    applying \Cref{lemma:single_counter_space}, the array occupies~$m = \sum_i
    O(1+\log_2 |v_i|) = O\left( w+\sum_i \log_2 |v_i| \right)$ bits. Due to the
    concavity of the logarithm, it must be that~$\sum_i \log_2 |v_i| \leq w
    \cdot \log_2(1/w \cdot \sum_i |v_i|)$. Because the logarithm is an
    increasing function and~$\sum_i |v_i| \leq N$, it must be that~$w \cdot
    \log_2(1/w \cdot \sum_i |v_i|) \leq w \cdot \log_2(N/w)$. Plugging this
    into the first expression in the proof yields~$m \leq O(w \cdot (\log_2
    (N/w) + 1))$. Recalling that the last sketch in \sketch's chain dominates
    the memory and that its arrays are of size~$\approx W(N)$ proves the
    result.
\end{proof}
When~$W(N)$ is a sub-linear power, the bound for \sketch\ in
\Cref{thm:all_counters_space} still holds when aggregating the sketches, since
the total increments and decrements in the last sketch is~$O(N)$. Yet,
when~$W(N)=\widetilde{O}(N)$, the total increments and decrements in the last
sketch is~$O(N \log N)$. As such, the space bound increases slightly by an
additive~$O(d \cdot W(N) \cdot \log\log N)$ bits.

\textbf{Memory Footprint Lower Bound.}
To prove a memory footprint lower bound for frequency estimation sketches, we
use them to implement filters and leverage their memory lower bounds. A filter
is a compact data structure that answers whether a query key exists in a given
set of keys. A filter never returns a false negative, but it may return a false
positive with a probability called the \emph{False Positive Rate (FPR)}. The
lower the FPR, the larger the filter's memory footprint must be. The following
theorem states a memory footprint lower bound for filters supporting sets of
unknown size:
\begin{theorem}[Theorem 3.1 of~\cite{PaghExpandability}, Simplified]
    \label{thm:filter_expandability}
    Letting~$n$ denote the size of a growing set of keys, any filter that
    maintains an FPR of at most~$\delta$ for this set at all times must have a
    memory footprint of at least~$n \cdot (\log_2 1/\delta + \log_2 \log_2 n) -
    \Theta(n)$ bits.
\end{theorem}
Therefore, a frequency estimation sketch that can be used to implement such a
filter must also use at least this much memory.

To illustrate the argument, consider a frequency estimation sketch with only
overestimation errors (e.g., CMS). Suppose this sketch guarantees an error of
at most~$E(N)$ and a confidence of~$1-\delta$ for streams of length~$N$. One
can use this sketch to implement a filter with an FPR of~$\delta$ over a set of
size~$N/(E(N)+1)$ by inserting each key~$E(N)+1$ times. Filtering proceeds by
checking if the frequency of a given key is at least~$E(N)+1$, returning a
positive if it is and a negative otherwise. Querying a key within the set
returns an estimate that is always at least as large as~$E(N)+1$ (i.e., a true
positive) while querying a key outside of the set only yields an estimate
of~$E(N)+1$ and above (i.e., a false positive) with a probability of~$\delta$.
As such, \Cref{thm:filter_expandability} must apply to this sketch:
\begin{theorem}
    Any frequency estimation sketch with only overestimation errors that
    processes growing streams with an error bound of~$E(N)$ and a confidence
    of~$1-\delta$ must have a memory footprint of at least~$\Omega(N/E(N) \cdot [\log 1/\delta +
    \log\log (N/E(N)])$ bits.
\end{theorem}
It is difficult to implement a filter with a sketch that has two-sided errors,
since underestimations may introduce false negatives. Nevertheless, we prove in
\Cref{sec:ommitted_proofs} that if the estimates of such a sketch have a
variance that yields an error bound of~$E(N)$ with a confidence of~$1-\delta$
(similarly to CS), the same lower bound holds:
\begin{restatable}{theorem}{thmsketchexpandabilitylabel}
    \label{thm:sketch_expandability}
    A linear frequency estimation sketch providing an estimate with a variance
    of~$E(N)/\delta$ for any key when processing a stream of size~$N$,
    uses~$\Omega\left( N/E(N) \cdot [\log 1/\delta + \log\log (N/E(N))]
    \right)$ bits of memory.
\end{restatable}

Recall from \Cref{thm:all_counters_space} that using a constant number of
arrays~$d$ for a constant confidence bound leads to a memory footprint
of~$O(W(N) \cdot (\log_2 (N/W(N)+1))$ bits for \sketch. One can verify that
when~$W(N)$ is a sub-linear power or a linear function, this memory footprint
can be expressed as~$O\left( N/E(N) \cdot \log (N/E(N)) \right)$ bits,
where~$E(N)$ is the error corresponding to the choice of~$W(N)$. This almost
matches the above memory lower bounds with a slight difference in the
logarithmic terms. Compressing the counter arrays by coarsely quantizing their
counter values and applying run-length encoding allows \sketch\ to match these
lower bounds.

\textbf{Performance.}
As \sketch\ handles insertions, deletions, and queries using the last sketch in
the chain, their cost is the same as the insertion or deletion cost of the last
sketch, i.e., $O(d)$ for \sketchcms. Moreover, the amortized cost of expansions
and contractions is constant, as they modify~$d \cdot W(N) \leq N$ counters
every time~$N$ more than doubles or halves.

\Cref{fig:mg_overview} presents an overview of MG. MG maintains an array of
slots, each storing a key (shown in gray) and a dedicated frequency counter
(shown in white). MG estimates the frequency of each key in the array as the
value of its counter. It returns an estimate of zero for the untracked keys.
When inserting a key~$x$, MG first checks if it has a dedicated counter in some
slot. If it does, MG increments~$x$'s counter. If not, and the array has an
empty slot, MG stores~$x$ in it with a count of~$1$. If~$x$ is not in the array
and the array is full, MG decrements all counters and discards any keys whose
counters become zero. Such keys are unlikely to be among the most frequent and
their slots are better used for tracking more frequent keys. Note that~$x$ is
not stored in the newly emptied slots and is only stored if it is inserted when
some slot is already empty. MG does not support deletions without deteriorating
the error bound~\cite{BatchUpdateMisraGries}. This is because it lacks
information about the untracked keys, which may become the heavy hitters after
the current heavy hitters are deleted, thereby failing to place them in its
array.

Having more slots in the array allows MG to track more keys without discarding
them, leading to more accurate estimates. Since MG is a deterministic data
structure that does not use hashing, unlike CMS and CS, it does not suffer from
hash collisions, and its estimations have full confidence. Using an array
of~$w$ slots, MG estimates the frequency of any key with an error of at
most~$\frac{N}{w}$, i.e., $|\hat{f}(x)-f(x)| \leq \frac{N}{w}$ for any key~$x$.
Since it uses dedicated counters for the heavy hitters, it also provides a
strong ``\emph{Tail Guarantee},'' stating that the error for any key is at
most~$\min_{1 \leq i \leq w} \frac{N^{\text{res}(i)}}{w-i+1}$, where
$N^{\text{res}(i)}$ is the total frequency of all keys not among the top~$i$.
Note that~$N^{\text{res}(i)}$ is much smaller than~$N$ when the data is skewed.

Since MG only increments a key's counter if it is in the array and decrements
counters otherwise, it only underestimates frequencies. Thus, its estimates are
biased. For similar reasons to CMS, this bias cannot be removed by enlarging
estimates. Yet, probabilistically replacing the array's least frequent keys can
yield unbiased estimates~\cite{UnbiasedSpaceSaving}. Other variations of MG
achieve higher accuracy in practice, but suffer from two-sided errors in
exchange~\cite{SpaceSaving}.

Typical implementations of MG use a hash table to implement the array of keys,
yielding constant-time queries. They also optimize insertions by lazily
decrementing the counters and employing an auxiliary heap to locate and discard
keys with zero counts. The query time can be further improved to~$O(1)$ using a
specialized data structures similar to a linked list in exchange for a higher
memory footprint~\cite{SpaceSaving}.

\textbf{Accommodating Skew.}
The counts stored in MG may still exhibit skew within themselves. This causes
memory wastage if uniformly-sized counters are used. \sketchmg addresses this
issue by storing the counter values in a separate array that mirrors the
ordering of the keys within the array of slots. It applies
\counterencodingabbrv to space efficiently encode these counter values. No
modification is required to \counterencodingabbrv, as the counter values are
all positive.

\textbf{Accommodating Skew.}
To bound the error for growing streams, \sketchmg generalizes MG to expand its
array of slots. Since keys are not hashed into the array of slots and can be
placed in any slot, \sketchmg expands this array on a slot-by-slot basis,
unlike \sketchcms and \sketchcs that double the size of their arrays.

\section{Omitted Proofs}\label{sec:ommitted_proofs}
\thmsketchexpandabilitylabel*
\begin{proof}
    It is impossible to implement a filter using a sketch with two-sided errors
    by thresholding the estimates. This is because underestimation errors may
    introduce false negatives. Nevertheless, we show taht the lower bound still
    holds by adapting the techniques used in the proof of Theorem~3.1
    in~\cite{PaghExpandability} to these sketches. At a high level, our proof
    follows a contradiction argument. We show that if a frequency estimation
    sketch~$\mathcal{S}$ with an error bound of~$\epsilon(N)$ and confidence
    of~$1-\delta$ exists that is ``too space-efficient,'' it can be used to
    compress many sequences of~$n=N/(\epsilon(N)+1)$
    keys~$\sigma=\sigma_1,\dots,\sigma_n$ coming from a large universe~$U$ of
    size~$u \gg N$ to a size smaller than their entropy, which must be
    impossible. We do this by simulating a filter as best as possible with the
    sketch, despite there being false negatives. Our argument holds regardless
    of the time complexity of~$\mathcal{S}$'s operations.

    First, we show that, w.l.o.g., we can assume that~$\mathcal{S}$ is a
    deterministic sketch which only has estimation errors larger
    than~$\epsilon(N)$ on a~$2\delta$ fraction of the elements in~$U$. We
    denote the fraction of such elements in~$U$ after inserting each of the
    sequence~$\sigma$'s keys $\epsilon(N)+1$ times into $\mathcal{S}$ as
    $\mu_{\mathcal{S}}(\sigma)$. We follow a similar argument to that of
    Section~3.1 in~\cite{PaghExpandability}:
    \begin{lemma}
        \label{lemma:derandomization}
        We can fix the internal randomness of the sketch~$\mathcal{S}$ such
        that, for at least half of the possible sequences~$\sigma$,
        $\mu_{\mathcal{S}}(\sigma) \leq 2\delta$.
    \end{lemma}
    \begin{proof}
        The randomized version of~$\mathcal{S}$ has a confidence of~$1-\delta$.
        Thus, denoting the internal random bits of~$\mathcal{S}$ by $r$, for
        any sequence~$\sigma \in U^n$, we have that~$\mathbb{E}_r\left[ 
        \mu_{\mathcal{S}}(\sigma) \right] \leq \delta$. Thus, by Markov's
        inequality, it holds that 
        $$ \Pr_r\left[ \mu_{\mathcal{S}}(\sigma) \geq 2\delta \right] \leq \frac{1}{2}. $$
        Considering the complement even yields
        $$ \Pr_r\left[ \mu_{\mathcal{S}}(\sigma) < 2\delta \right] \geq \frac{1}{2}. $$

        all sequences.
    \end{proof}
