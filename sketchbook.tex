\section{Introduction}~\label{sec:introduction}

\section{Background}~\label{sec:background}
A na\"ive approach to tracking the frequency of elements in a stream is to
store each element and its count in a hash table. While accurate, this
solution's memory overhead is prohibitive, as it stores all elements in the
dataset, using linear memory, and each of its counters must be large enough to
accommodate the maximum count, which is often unnecessary. This overhead is
exacerbated if the elements are variable-length strings (due to needing to
store pointers) and if the sketch must monitor multiple streams. The classical
Count-Min Sketch~\cite{CountMin}, Count Sketch~\cite{CountSketch}, and
Misra-Gries~\cite{MisraGries} data structures overcome this issue by trading
accuracy for space. They also form the basis upon which most other sketches are
designed. These data structures handle skew at varying levels of efficacy.

\textbf{Stream Model.}
In some applications, such as tracking click-through rates in webpages,
elements (clicks) are only inserted. In others, such as maintaining frequency
estimates for SQL table entries for use in a query optimizer, elements (rows)
can also be deleted. We model both types of streams as a sequence of element
and update operation pairs~$\left\langle (x_1,\Delta_1), (x_2,\Delta_2), \dots,
\right\rangle$, where each~$x_i$ is an element and~$\Delta_i = \pm1$ represents
whether it was inserted ($\Delta_i=1$) or deleted ($\Delta_i=-1$). This is
known as the \emph{General Turnstile Model} of data
streams~\cite{StreamModels}. Supporting deletes appears to be more challenging
than supporting only inserts, since some sketch designs fail to do
so~\cite{MisraGries,BatchUpdateMisraGries}. At any point, $N=\sum_i \Delta_i$
represents the total number of elements in the stream. Given a data stream, for
any element~$x$, a frequency estimation sketch provides an
estimate~$\hat{f}(x)$ of the number of times~$f(x)$ it has appeared in the
stream. \Cref{tab:term_and_symbol_definitions} lists the terms and symbols used
throughout the paper.

\textbf{Count-Min Sketch (CMS).}
In its simplest form, CMS employs an array of~$w$ counters initialized to
zeros. It inserts an element~$x$ by mapping it to a counter in the array using
a hash function and incrementing the counter. CMS estimates the frequency
of~$x$ as the counter value it hashes to. This is, on average, a good estimate
of the frequency, as other elements likely map to different counters,
allowing~$x$'s counter to mainly track~$x$'s frequency. The wider the array is,
the more likely this separation of counters and the better CMS's
\emph{Accuracy} becomes. CMS deletes~$x$ by decrementing its counter. Compared
to the exhaustive hash table solution, CMS consumes significantly less memory
since it avoids storing the elements themselves and allocates a constant number
of counters.

Yet, due to hash collisions, multiple elements can map to the same counter.
Because of this, unlike the exhaustive approach, CMS may overestimate
frequencies, but it never underestimates. This error is expected to be small,
though it may become exceedingly large if there is a collision with a different
frequent element or many other elements. To control the likelihood of this
event and bound the error, CMS treats its array as a frequency estimation
``experiment'' and repeats it~$d$ times with independent arrays and hash
functions~$h_1,\dots,h_d$. \Cref{fig:sketches_overview} shows an example of
this repeated structure. CMS now answers a query by taking the minimum of its
counters in all~$d$ arrays.\footnote{CMS ensures that this reduces the
estimation error by employing pairwise-independent hash functions
for~$h_1,\dots,h_d$. Doing so provides a bound on the probability of collisions
and overestimation.} Having more experiments improves CMS's \emph{Confidence},
as it becomes increasingly unlikely for the minimum to experience severe errors
since it requires all experiments to err significantly.
Using~$w=\frac{e}{\epsilon}$ counters and~$d=\ln \frac{1}{\delta}$ repititions,
CMS ensures estimates have an error of at most~$\epsilon N$ with a confidence
of~$1-\delta$, i.e., $\Pr\left( |\hat{f}(x)-f(x)| \leq \epsilon N \right) \geq
1-\delta$ for any element~$x$.

CMS produces a biased estimator due to its one-sided overestimation errors.
These errors compound when the sketch is used in some tasks, particularly those
that involve multiplying frequencies. These errors cannot be eliminated by
discounting the results, as amount depends on the unknown ground-truth
frequency.
%For example, in join size estimation, multiplying overestimated counts from the input tables leads to an overly large join size.

\textbf{Count Sketch (CS).}
CS removes such systematic errors and provides unbiased estimates. Similarly to
CMS, CS uses an array of~$w$ counters coupled with a hash function~$h_i$ that
maps a given element to a counter that tracks its frequency. CS further
associates with each element a random ``update direction'' from the
set~$\{-1,+1\}$ by hashing it with another hash
function~$\sigma_i$.\footnote{The~$\sigma_i$ form a 4-wise independent family
of hash functions, yielding a bound on the probability of large
errors~\cite{CountSketch}.} It inserts a new element~$x$ by incrementing or
decrementing its counter according to~$\sigma_i$, as shown in
\Cref{fig:sketches_overview}-B. Since each element's update direction is
random, the expected interference on~$x$'s counter from any other element is
zero, as the positive and negative possibilities cancel out. Thus, the value of
the counter along the update direction is an estimate of~$x$'s frequency, which
CS returns during a query. Although this estimate may be smaller or larger than
the ground-truth frequency, depending on the update directions of the other
items, the zero expected interference makes the estimate equal to the
ground-truth on average, resolving systematic errors. CS deletes~$x$ by
subtracting~$\sigma_i(x)$ from its counter to undo its insertion effects.

Hash collisions still degrade the accuracy of this estimate. Having more
counters in the array makes such collisions less likely, yielding better
accuracy. As with CMS, CS increases its confidence (i.e., reduces the chances
of pathological hash collisions) by treating the array as an experiment and
repeating it~$d$ times. Unlike CMS, CS cannot answer a query by returning the
minimum estimate, as it may greatly underestimate the result due to two-sided
errors. Instead, it returns the median estimate, as shown in
\Cref{fig:sketches_overview}-B. This controls the likelihood of large errors,
since severe errors are unlikely to occur for enough experiments to affect the
median. CS uses the median instead of the mean, as it is more robust to
outliers. Using~$w=\frac{e}{\epsilon^2}$ counters and $d=\ln \frac{1}{\delta}$
repititions, CS guarantees a high confidence of~$1-\delta$ for an estimate with
an error of at most~$\epsilon \cdot \sqrt{\sum_{y} (f(y))^2}$, i.e., $\Pr\left(
|\hat{f}(x)-f(x)| \leq \epsilon \cdot \sqrt{\sum_{y} (f(y))^2} \right) \geq
1-\delta$ for any element~$x$. The error term above is smaller than CMS's error
term when the frequency distribution is less skewed, as the root slows its
growth to~$O(\sqrt{N})$ (vs.~$N$) when the summands are small.

\textbf{Misra-Gries (MG).}
As skew increases, using dedicated counters to track the hottest elements
becomes more beneficial than hashing them into an array of counters, like CMS
and CS. By applying this insight, MG provides more accurate estimates in these
scenarios. Although certain variations of MG provide better estimates in
practice~\cite{SpaceSaving,UnbiasedSpaceSaving}, we describe the original MG
for its simplicity and because our techniques generalize to the improved
variations.

\Cref{fig:sketches_overview}-C shows an overview of MG. MG maintains an array
of slots, each storing an element identifier (shown in grey) and a dedicated
frequency counter (shown in white). The idea is to track the frequencies of the
hottest elements in this array. MG estimates the frequency of each of these
elements as the value of its counter, yielding a good estimate. It returns an
estimate of zero for the other, less frequent elements, which is not far off
from the ground-truth due to the assumption of high skew. When inserting an
element~$x$, MG first checks if it has a dedicated counter in some slot. If it
does, MG increments~$x$'s counter. If not, and the array has an empty slot, MG
stores~$x$ in it with a count of~$1$. If~$x$ is not in the array and the array
is full, MG decrements all counters and discards any elements whose counters
become zero. Such elements are unlikely to be among the most frequent, and as
such, MG empties their slots to make room for tracking hotter elements. Note
that~$x$ is not placed in the newly emptied slots in this case. MG does not
support deletions, as deleting the currently hot elements may make the
untracked elements the hot ones. Since MG did not track these elements, it
cannot place them in its array, incurring significant errors. MG is much more
space-efficient than the exhaustive hash table solution, as it only stores a
constant number of element and counter pairs.

Having more slots in the array allows MG to track more elements without
discarding them, leading to more accurate estimates. Since MG is a
deterministic data structure that does not use hashing, unlike CMS and CS, it
does not suffer from pathological hash collisions, and its estimations have
full confidence. Using an array of~$w$ slots, MG estimates the frequency of any
element with an error of at most~$\frac{N}{w}$, i.e., $|\hat{f}(x)-f(x)| \leq
\frac{N}{w}$ for any element~$x$. Since it uses dedicated counters for hot
elements, MG also provides a strong ``\emph{Tail Guarantee},'' stating that the
error for any element is at most~$\min_{1 \leq i \leq w}
\frac{N^{\text{res}(i)}}{w-i+1}$, where $N^{\text{res}(i)}$ is the total
frequency of all elements not among the top~$i$. Note that~$N^{\text{res}(i)}$
is much smaller than~$N$ when the dataset is skewed.

Since MG only increments an element's counter if it is in the array and
decrements counters otherwise, it only underestimates frequencies. Thus, its
estimates are biased. For similar reasons to CMS, this bias cannot be removed
by enlarging estimates.

Typical implementations of MG implement the array of elements with a hash
table, yielding constant-time queries. They also optimize insertions by lazily
decrementing the counters and employing an auxiliary heap to locate and discard
elements with zero counts.

\textbf{Comparison.}
\Cref{tab:classical_sketch_stats} summarizes the discussion of CMS, CS, and MG
thus far by comparing their attributes. While \Cref{tab:classical_sketch_stats}
compares the error bounds of the sketches, we further illustrate their
differences by evaluating the sketches under varying levels of data skew and
memory budgets. Here, we insert 100M keys drawn from the \textsc{Zipfian}
distribution into each sketch. We vary the characteristic exponent of the
distribution to control the skew of the data. We evaluate the \emph{Average
Absolute Error (AAE)} for each sketch by querying each element in the stream,
computing the abosulte difference of estimate from the ground-truth, and
averaging the results.

\Cref{fig:classical_comparison} plots these results. As shown in the left
subfigure, CS beats the others under less skew, as the updates of elements with
similar frequencies cancel out when their hashes collide. In contrast, such
collisions in CMS accumulate the error, and MG has insufficient slots to track
elements accurately. Under moderate skew, CMS performs the best. This is
because taking the minimum estimate increases confidence and bounds the error
more reliably than the median method of CS. MG closely follows the performance
of CMS as it benefits more from the increasing skew. Eventually, MG surpasses
both CMS and CS by fully leveraging its dedicated counters and even achieves
zero error under high enough skew.

The right plot in \Cref{fig:classical_comparison} illustrates that, under
extreme memory constraints, MG outperforms CMS and CS. This is because CMS and
CS do not have enough counters, leading to too many hash collisions and overly
large estimates, whereas MG makes the most of its limited counters by
leveraging its tail bound. Here, CS bests CMS due to its zero-interference
property, making it more robust to hash collisions. Given more memory, CMS and
CS outperform MG, with CMS beating CS by benefiting more from the minimum
estimate than CS does from the median. With more memory, MG tracks all elements
and provides the most accurate estimations, whereas CMS and CS's estimates
still suffer from collision errors.

CMS and CS are faster than MG since they read and write a single counter in
each array, while MG has to pay the logarithmic cost of maintaining the heap
and the added cost of the hash table.

\textbf{Applications.} 
Due to its simplicity and high accuracy under moderate skew, CMS is used in
applications with moderately skewed data, including $k$-mer counting in
bioinformatics~\cite{CMSkmer,SetMinSketch}, network
monitoring~\cite{SketchBasedChangeDetection,WhatsNew,TrafficManagementSurvey},
and hardware security systems~\cite{CoMeT}.

Since CS provides unbiased estimates, it is used in applications where
estimates are combined or multiplied to derive more complex statistics. In
particular, unbiased estimation is crucial for query
optimization~\cite{Compass,QueryOptimizationSketches,ConvolutionSketch} and
covariance estimation~\cite{ASCS}, as frequency estimates are multiplied in
these contexts, amplifying any bias. Other applications benefiting from CS
include feature selection~\cite{MISSION} and similarity
search~\cite{CSSetSimSearch,DensifyingLSHSketches,LasVegasSimSearch,DistanceSensitiveBloomFilters}.
CS also provides \emph{Universality}~\cite{UniversalSketching}: the ability to
estimate many statistics based on the element frequencies. This makes it a
general measurement tool for networks since it allows administrators to collect
diagnostics of any kind without needing to explicitly define the required
statistics (such as the mean, variance, and moments) beforehand~\cite{UnivMon}.

As MG accurately tracks the frequencies of hot elements, many other sketch
designs use it as a sub-component to reap its benefits. Moreover, because it
also stores the elements themselves, unlike CMS and CS, it is used to report
the hottest elements, trending elements, and much
more~\cite{BatchUpdateMisraGries,AugmentedSketch,BitMatcher,BubbleSketch,HeavyGuardian,HeavyKeeper,JigsawSketch,MVSketch,SketchVisor,WavingSketch,MicroscopeSketch,PSketch}.

\section{Problem Analysis}\label{sec:problem_analysis}

\section{Sketchbook}\label{sec:sketchbook} 
We present Sketchbook, a general method of expanding sketches to handle streams
of unknown size and achieve better space utilization.
\Cref{sec:expanding_columns} describes how Sketchbook guarantees a lower error
bound by expanding the number of columns (or slots) along with the number of
elements in the stream. Specifically, it utilizes an \emph{Expansion Rate
Function} to decide when to expand. The larger this function is, the earlier
the sketch expands and the more accurate it becomes, exposing an accuracy-space
tradeoff. \Cref{sec:expanding_counters} describes how Sketchbook makes use of
variable-length counters that expand to accommodate the value they store,
improving accuracy by minimizing unused bits in the counters. Sketchbook
employs lookup tables and rank and select operations to efficiently manipulate
these counters. We do not discuss the idea of expanding the number of rows in
CMS and CS since it does not yield a significant benefit in accuracy or
confidence, as shown in \Cref{sec:theoretical_analysis}. For concreteness, we
describe our techniques applied to CMS as a running example and comment on how
they can be applied to CS and MG.

\subsection{Expanding Columns}\label{sec:expanding_columns}

\textbf{Expansion Rate Function.} 
Introduce the expansion rate function~$R(N)$. The idea is to maintain~$R(N)$
columns in the sketch at all times to ``emulate'' the case where we knew~$N$
and started with a sketch with~$R(N)$ columns. The hope is to approximately
achieve the same error bound as this sketch, i.e., $N/R(N)$.

\textbf{Chain of Sketches.} 
Explain that we maintain a chain of sketches, with each sketch being twice the
size of the sketch before it. Say that updates go to the final sketch in the
chain, as it is the most accurate, but queries have to check all sketches.
Explain that this sketch acts like a single, unified sketch the size of the
last sketch in the chain, and connect it back to the size intuition above.
Point out that the space is good since the total size of the chain is dominated
by the last sketch. We use the same hash function across all sketches to save
CPU.

\textbf{Expansions.} 
To expand, we add a new sketch double the size of the previous one each time
the expansion function doubles. Give intuition about how this maintains
approximately~$R(N)$ columns/slots at any point in time with the hope of
achieving the same behavior as a sketch of size~$R(N)$ allocated with knowledge
of~$N$. Doing so controls the total error as the sum of a geometric series.

\textbf{Aggregate Sketch.}
Having to work with the entire chain and to query all sketches in it is slow.
To avoid this cost, we create an aggregate sketch that takes into account all
sketches in the chain. Explain the sketch doubling method for CMS and CS and
that it allows us to keep using the same hash function across time. To save
memory and avoid storing the aggregate sketch as well, we ``replace'' the last
sketch in the chain with the aggregate sketch. Argue that this does not create
information loss, as we reconstruct the last sketch by ``subtracting out'' the
old ones. 

Point out that for MG, as it doesn't use hashing and is more of an associative
array, we expand on a slot-by-slot basis to exactly match~$R(N)$, yielding
potentially higher accuracy. 

\textbf{Contractions.} 
Explain that we have to shrink the sketch to save memory if too many keys are
deleted. Specifically, when the expansion rate function is halved, we
reconstruct the final sketch in the chain by ``subtracting out'' the other
sketches from the aggregate sketch. As a result of this subtraction, some
counters may be positive, signifying inserts, and some may become negative,
signifying deletes. As such, it behaves like an ``update sketch,'' which
``fold'' onto itself to make it the same size as the previous sketch in the
chain and add them to propagate back the updates. 

Give intuition that the error bound remains good, as the old sketches contain a
small fraction of keys, and a lot of keys must be deleted for a contraction to
occur. Also point out that now, the state of the sketches in the chain depends
on the sequence of inserts and deletes done. Regardless of the sequence,
however, the error bounds hold.

\textbf{Physical Storage.}
If we only want to support inserts, we physically manifest only the aggregate
sketch to save memory. For deletes, since we have to subtract out the old
sketches during contractions to reconstruct the final chain sketch, we need to
store the entire chain.

\subsection{Expanding Counters}\label{sec:expanding_counters}

\textbf{State of the Art.} 
Reiterate that using fixed-sized counters is bad, since most counters will have
small values, and thus their higher-order bits are left unused, wasting space.
Point to the backgroun section with a review of existing variable-length
counter encodings, and explain Stingy Sketch as the state of the art in terms
of both accuracy and speed. 

\textbf{Sharing of Higher-Order Bits.} 
State that the key problem in such methods is that higher-order bits in the
counters are shared. This is counter-intuitive, since higher-order bits have
more impact on the accuracy of the sketch, and sharing them opens up the door
to unwanted errors. Moreover, it complicates deletes, as it is no longer
possible to ``separate out'' the counters that share some higher-order bits
from each other as soon as possible to improve accuracy. An attacker may be
able to use this behavior to radically increase the error of the sketch with
time. So we propose not sharing any parts of the counters to resolve all these
problems.

\textbf{Base Counters Array.} 
Given a logical array of counters, Sketchbook encodes it by first allocating an
array of small, $b$-bit counters to each. Each base counter encodes the~$b$
least-significant bits of its logical counter. Here, $b$ is a tuning parameter
denoting the width we expect each counter to be. We have found~$b=6$ is
reasonable for many sketch configurations. As the some logical counters can
grow beyond the range of~$b$-bit counters, we require another mechanism to
succinctly encode the remaining higher-order bits of these counters.

\textbf{Overflowed Bitmap.} 
To this end, we employ a contiguous overflowed bitmap to indicate which base
counters have reached their limit and have overflowed. For any overflowed
counter, we encode the remaining higher-order bits using~$b'$-bit extensions.

\textbf{Extensions Array.}
Explain that the~$b'$-bit extensions represent the value of the counter's
higher-order bits in base-$(2^{b'}-1)$. Explain that we pack all extensions
contiguously into an extensions array, forming runs. State that we reserved one
of the~$2^{b'}$ values to act as a delimiter between the runs. Give a sense of
the total space overhead one can expect for the average counter.

\textbf{Locating a Run.}
Introduce rank and select and state that we apply them along with some bitwise
operations to the extensions array to locate the end of a run.

\textbf{Decoding Counters.}
Explain how we decode a counter given the encoding above.

\textbf{Spill Mechanism.} 
In unlikely scenarios, the extensions array may fill up and make the sketch run
out of space. Inspired by frontyard/backyard hash table designs, we implement a
``spill'' mechanism that activates when the extensions array fills up. Here, we
employ a flag in the extensions array to denote whether we are in the spilled
state. If we are, the extensions array stores a pointer to an array of full
counters, which will now store the values of the counters, modulo the $b$
least-significant bits already stored in the base counters. We expect the
memory overhead of the spill mechanism to be very small, as it is only
activated in the unlikely even of the extensions array filling up.

\textbf{Chunking.} 
Describe how we apply the our techniques to chunks of 64 counters each to
minimize the amount of extension shifting and to further reduce the memory cost
of the spill mechanism. Go into details as to how having 6-bit base counters
and 2-bit extensions allows us to fit the encoding of these 64 counters neatly
into a 512-bit cache line, yielding good cache behavior.

\textbf{Optimizations.}
Explain how we use lookup tables to speed up updates to the base counters and
how we use x86 instructions to speed up rank and select.
